# V8 forward matmul precision diagnosis R1

This diagnosis checks whether TPU-default reduced-precision dot products could explain part of the V8/PyTorch forward gap. It verifies the actual Kaggle entrypoint and parameter flow before comparing arithmetic on the CPU.

[Source audit](SOURCE_AUDIT_R1.json) pins the executed `probe.py`, the staged JAX RNN source, the updated EMA checkpoint and the full-sequence producer output. V8's child worker imports JAX and calls the V8-local `run_device_worker`; it does not invoke the separate E465 helper that sets `jax_default_matmul_precision="highest"`. V8 passes `precision="fp32"` for model compute dtype, but `_linear` and GRU matmuls have no per-dot precision. The Kaggle worker receives a copy of the parent environment, and the launch receipt does not preserve the inherited JAX precision variable, so the runtime setting is unknown.

The producer receipt shows that V8 exported the full20k prediction with `reloaded_ema`, after bitwise save/reload, and embedded that EMA file's SHA in the prediction archive. The source-qualified sequence is `valid/254` (`seq_ix=267134787`). The locally rebuilt NumPy-engineered 211-feature input matches the producer's full-sequence input hash. Local data and feature module hashes match the V8 source materialization; the current `RNNModel` source includes later equal-width-compatible options, and its use is checked against the independent manual replay. Targets and scoring masks were not loaded for this comparison.

[CPU result](NUMERICAL_DIAGNOSIS_R1.json) reports the first137 rows. A manual replay of the frozen FP32 JAX equations agrees with PyTorch within5.72e-6 across23 outputs,4.17e-7 on the two primary outputs, and5.67e-7 on final state. Only after this control passed did the script run a surrogate that rounds both operands of each matmul through BF16, then accumulates/adds bias and applies normalization, exact GELU, sigmoid, tanh, gates and recurrent state in FP32. On these rows the surrogate reduces the main2 PyTorch-to-TPU max error from0.0047563 to0.0027083 (mean0.0012838 to0.0005393; RMS0.0016394 to0.0007586). It does not remove the gap and raises the all23-output maximum from0.05577 to0.06703. This supports a main2-specific reduced-dot hypothesis on the tested prefix; it does not prove which compiler dot mode V8 used.

The run used Python3.13.9, Torch2.14.0 and NumPy2.2.6, one thread and the admitted one-core/1.5GB/120-second scope. Manual/surrogate compute after input and model loading took0.192s; process peak RSS was826MB. The short-lived systemd scope did not retain a cgroup peak counter. The raw [attempt receipt](ATTEMPT_R1.json), [stdout](ATTEMPT_R1.stdout) and [stderr](ATTEMPT_R1.stderr) pin the command and output. Ruff and Python bytecode compilation passed.

The JAX authors' [matmul precision guide](https://docs.jax.dev/en/latest/201/precision.html) says TPU FP32 dots at `Precision.DEFAULT`/`None` use BF16 arithmetic by default; global defaults can be overridden. Because V8 did not capture that inherited setting, treat this as a plausible mechanism with CPU-surrogate support, not an established cause. Only137 local rows were replayed; no full20k CPU replay, score, quality claim, fitting, JAX install, GPU, TPU or cloud action was performed. The sequence was already fitting data.
