The scope was the RAM-headroom correction, including concurrent-admission accounting and race behavior. The commit changes only `scripts/bandit_resources.py` and its focused tests. The GPU policy and legacy-path findings from R1 remain applicable because this commit does not alter those paths.

The new guard fixes R1's concrete overcommit case. With 10 GB parent use, an active worker reserving 12 GB and using 8 GB, and a new 4 GB bound, `verify_capacity()` computes `10 + (12 - 8) + 4 = 18 GB` and rejects against the 17 GB committed target. With a 3 GB new bound it computes exactly 17 GB and admits; the worker's current 8 GB is not counted a second time. The tests exercise both outcomes (`tests/test_bandit_resources.py`, `test_active_worker_unused_reservation_blocks_ram_overcommit` and `test_active_worker_use_is_not_double_counted_in_ram_headroom`).

The launch path writes its own preflight ledger entry before admission and passes that attempt ID as `exclude`, so its unresolved record does not block itself. A different unresolved record still blocks admission. Active `waiting` entries are included. If their unit/cgroup is missing, outside the parent, invalid, or vanished, the code retains the full reservation as unused headroom; it does not treat unknown usage as zero. The launch recheck samples the parent after active worker cgroups and retains the largest caller/inside parent sample, which catches the tested parent-growth race.

One residual limits simultaneous RAM admission. Cgroup reads are sequential rather than an atomic snapshot. For example, if parent use was 9 GB at the earlier caller sample, the active worker reads 9.5 GB, then that worker falls to 8.5 GB as other parent use grows and the later parent sample reads 10 GB, the code projects `10 + (12 - 9.5) + 4 = 16.5 GB`; the coherent contemporaneous projection is `10 + (12 - 8.5) + 4 = 17.5 GB`. The added ordering test catches parent growth between the caller and internal parent samples, but does not rule out this worker-drop/other-growth direction. This does not block the fresh first GPU attempt with zero active ledger workers. Until this race is addressed, any overlapping support admission should use the full active-worker reservation in the manual parent-memory check or wait until the worker finishes; do not rely on the sampled-unused-reservation discount for that overlap.

The relevant inherited policy checks also remain sound on the chosen durable path: CPU admission is limited to five cores, aggregate systemd properties require 18 GB `MemoryHigh`, 20 GB `MemoryMax`, and zero swap, and per-attempt services are directly placed beneath the same aggregate slice. The existing `state/gpu.lock` serializes admitted local GPU workers. The selected `bandit_resources` launch/service path no longer injects the old 4.3 GB PyTorch allocator cap or rejects observed use at 5 GB. `configure_torch()` derives its allocator fraction from CUDA free/total bytes at startup minus the configurable safety reserve; this is a startup snapshot, not continuously rebalanced. The reserved environment checks and currently installed watcher/queue path findings are unchanged from R1: the alert-only watchers do not enforce the withdrawn 5 GB threshold, while the legacy local queue remains stopped. Separate legacy campaign launchers still carry old limits and must not wrap this fit.
