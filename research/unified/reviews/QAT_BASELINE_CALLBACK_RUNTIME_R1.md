# Xteam H4 baseline callback runtime R1

The unchanged four-member `xteam_h4` package completed a bounded callback benchmark on two complete validation sequences, with state reset before each pass and bitwise-identical predictions over two repeats. The canonical run used the existing Python 3.11.16 profile environment, native v3 Q8VNNI dispatch and CPU affinity `[0]`. It measured 89.678249 microseconds per callback-row over 80,000 calls; the measured callback time was 7.174 seconds and wall time after sequence decode, including extraction and import, was 11.754 seconds. The fixed sequences were row groups 4 and 5, IDs 1990332 and 2308749.

The [R3 binding](../../campaign_2026-10-13/qat_renewable_r1/final_release_r1/BASELINE_BENCHMARK_BINDING_R3.json) corrects the interpreter path while preserving the ZIP, four members, native libraries, data, row groups, repeats and benchmark implementation. It pins the Python 3.11 result at `artifacts/qat_renewable_r1/final_release_r1/BASELINE_CALLBACK_RUNTIME_R3.json`, SHA256 `a71515f86f01ce8caaabef29e777aece4ba344a34a421cb7444ac6b22482b476`. The runner verifies ZIP CRC and member hashes and hashes the full 5.6 GB validation parquet before and after the run. Temporary extraction used the physical Btrfs path recorded in the [machine receipt](receipts/QAT_BASELINE_CALLBACK_RUNTIME_R1.json).

The first execution under the R2 binding is preserved at `BASELINE_CALLBACK_RUNTIME_R2.json`, SHA256 `7b56736d6bdba152e5921725f44938220b7a70d9b818c018013e71c9cc154c54`; although it completed, it used Python 3.13.9 because the main `.venv` did not match the assigned Python 3.11 profile. It is not used for cross-package timing. The R3 measurement is the Python 3.11 reference.

The R3 worker reached its 1 GB memory ceiling while hashing the parquet: its cgroup peak was 999,997,440 bytes and the maximum-limit counter increased, but OOM and kill counters remained zero and the command exited successfully. Treat this as a completed runtime point under a saturated worker cap, not a memory-headroom result. Only two sequences and two repeats were measured, so this is not a full-panel latency distribution. The callback timing excludes parquet decoding and state reset, and no score was computed. A candidate timing is directly comparable only with the same Python environment, CPU affinity, native dispatch, row groups, repeat count and resource caps; root owns the matched candidate benchmark and release decision.
