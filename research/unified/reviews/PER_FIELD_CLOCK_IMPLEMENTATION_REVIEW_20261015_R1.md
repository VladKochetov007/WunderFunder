# Per-field clock implementation review R1 — 2026-10-15

This is a bounded, read-only source review of commit `bc0f223e15be8d5190a76894c770d9ca80630863` in `/home/vlad/development/wunder/worktrees/per-field-clock-20261015`. I did not run tests, read feature payloads, profile a model, or launch a fit. The source semantics look causal and append-only, but the current R1 recipe is not a runnable fit/export contract.

`field_age` compares each float32 raw input column with the preceding row, resets that column's age to zero on a change, increments it otherwise, caps at 10,000, and returns `log1p(age)`. `group_age` applies the same rule to the seven declared raw-column ranges and broadcasts each range's age. Row zero starts at zero. The transforms use only raw input rows and cannot use future rows, labels, masks, or teacher outputs.

The trainer's `build_inputs` computes research features from the complete `(B,T,112)` raw tensor before recurrent chunks are sliced. `predict` calls the same builder before chunked forwarding; `predict_run.py` restores the feature mode from checkpoint arguments and leaves the moment-prior path disabled for age modes. Recurrent state is initialized for each prediction call and carried only between chunks. The existing `none` mode remains the default and continues to assemble the 112 raw plus 99 event features (211 inputs). The native C++ consumer does not implement these modes, as the campaign README already states; this review gives no native compatibility or deployment approval.

The initializer expansion is function-preserving in source-level arithmetic: `can_extend_research_features` admits the append-only mode, `expand_research_feature_state` copies the old input projection and normalization buffers, zeroes the 112 new projection columns, and assigns the added features mean zero/std one. This preserves the parent's initial predictions when the rest of the model and feature layout match. That parity has not been executed against the actual parent checkpoint.

The committed tests contain a useful independent row-wise oracle for the NumPy batch transform and compare the streaming implementation across chunk boundaries, resets, and future perturbations. They do not exercise `_field_age_features_torch`, which is the path used by `train_rnn.build_inputs` and therefore by training and `predict_run`. Add one small CPU test comparing both Torch modes against the existing independent oracle on the same sequence panel. This is the minimal unresolved implementation check before fitting; the current oracle shares `RAW_FIELD_GROUPS` and the age cap with production, so it independently checks the recurrence but not those chosen range definitions.

There is also a concrete export-membership error in the R1 campaign README. It says to predict all 1,405 valid groups, but the frozen F0 records distinguish 1,405 `valid_fit` groups, 468 official evaluation groups, and 1,873 groups in the full valid source. `predict_run.py` with the default campaign-valid selector uses `manifest.valid_groups` (the fit-valid set); the full-valid feature-only selector exports 1,873, and the evaluation-only selector exports the exact 468 scored groups. An export of 1,405 cannot support the stated 468-group official grade. Correct the successor recipe to pin either the 1,873 full-valid order or the exact 468 evaluation membership and verify its prediction count against the grade input.

The R1 README is explicitly a six-epoch proposal. Root's intended next screen is a matched two-epoch C/G/F comparison from the selected warm parent. Keep the frozen R1 note as historical preparation and issue a new R2 contract that pins that changed horizon, exact fit membership/order/update count, and the corrected export selector. The R1 proposal itself should not be used as a launch packet. No score, quality gain, independent GPU behavior, or serving result follows from this review.
