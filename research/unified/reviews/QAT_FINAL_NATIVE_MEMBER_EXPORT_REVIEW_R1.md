This is a bounded consumer review, not a score, package, or quality approval.

The reviewed source is MAIN commit `3d8b1088552fab1806a180fc54412bebc0466428`, `scripts/export_native_qat_member_panel.py`, SHA256 `1e6550d6af562ac462cfca0c984d7c24f7d6c29ec14759d339a92c49f49b16ee`. The program checks caller-supplied SHA256 values for the weights/archive, native extension, split and data before loading them. In packed mode it calls `read_packed_quantized_export` and gives the decoded exact codes to `EnsemblePredictor` with `precision="q8vnni"`; the raw-NPZ path passes the effective float32 weights for native dynamic-Q8 inference. These are distinct transports and their manifests must remain separate.

For each selected row group, the exporter validates a complete 20,000-row sequence and canonical step order, resets the native model, and feeds every feature row through `EnsemblePredictor.step`. The native `step` calls the same `advance()` processing path as the callback; the explicit per-group reset supplies the state boundary. Scoring uses `need_prediction & is_scored`, matching the local step-by-step scorer. It streams selected targets and predictions through `utils.GlobalAccumulator`, the repository's standalone official pooled clipped weighted-Pearson implementation. The source stores a complete first sequence and compares its exact outputs after traversing the remaining groups and resetting, so the check is a full-sequence A-to-B-to-A replay.

The prediction matrix is a float32 memmap with shape `(number_of_groups, 20000, 2)`. It flushes and advises pages away every eight groups; progress is append-only. The final result records the actual ordered groups, input hashes, score, output hash, and an explicit fitted-data/no-held-out/no-public-claim scope. Static resource review found one operational caveat: hashing the full parquet can warm its page cache, and hashing the finished prediction file can repopulate roughly 75 MB per 468-group panel after the periodic evictions. Include current memory/file-cache headroom in root admission and reclaim cache after the run if necessary.

Therefore the run receipt must bind the exact frozen F0 split SHA and verify that `result.json` contains its exact ordered 468 groups before these member vectors enter a four-way comparison. This is an invocation-level condition, not a defect in the row processing. I did not execute the full parquet scan, native inference, or score; verify neither actual runtime nor profile-level memory here. All reviewed groups are exposed F0 fitting/adaptation diagnostics, not clean CV or public-transfer evidence.
