# Independent review: PR49 teacher-pool import, R1

## Scope and disposition

Read-only critic of the PR49-backed pool import and its proposed strict-source student comparison. I inspected the requested packet, the original release ZIP, its provenance JSON, the pinned source files, and the current distillation-target construction. No model was loaded, no fit or GPU work was run, and no score was used to approve the pool.

**Import, membership, and inference-source checks pass. One concrete pre-fit check remains:** bind the student’s actual train-target tensor to the intended `.34/.33/.33` pool. The current `--distill` implementation averages scaled teacher predictions by the number of teachers, so passing those coefficients as scales directly would divide the intended mixture by three. The validation grade does not exercise this student-target construction.

## Checks that pass

- **Release and metadata adaptation.** The ZIP digest is `02899081e9576bd86a0197cb3eae5bd1ccc8a4b1c26e1669cd1e10a62efd31fa`, as recorded in [`IMPORT_R1.json`](IMPORT_R1.json). The importer compares every split field except `sources`, then checks source-qualified parquet byte size/footer identities and index byte/content identities. It records both manifest digests and explicitly describes the timestamp/cache-identity differences. Its adaptation changes run name and local manifest binding while retaining original run, checkpoint, provenance, and split identities; it does not silently claim the two manifest files are byte-identical.
- **Model payloads.** I compared each producer checkpoint’s PyTorch ZIP storage members to the imported checkpoint with standard-library archive reads. Storage member names, counts, lengths, and bytes match for all three models: FBC 16 members / 3,925,748 bytes; each TLead 24 / 4,264,852 bytes. The outer checkpoint hashes differ as expected after metadata serialization and match the imported hashes in the receipt. The importer also contains a per-state-dict-key `torch.equal` assertion; I did not rerun that torch load under this review’s no-extra-load constraint.
- **Recursive fit ancestry.** All 16 archive provenance records resolve into a closed acyclic parent graph. Every record uses `train_source=train`, `include_heldout_valid=false`, the exact 10,325 train groups, zero valid fit groups, and the declared 1,873 valid evaluation groups. The importer checks distillation-parent bindings; I additionally checked all 12 referenced initializer/distillation parent checkpoint bytes against their recorded hashes, with no mismatch. The three selected models are fixed epoch-3 checkpoints; the two TLeads share the same two declared distillation parents. Group identities are source-qualified, so integer row-group IDs from different parquet files must not be compared as if they shared one namespace.
- **Source compatibility.** Each selected producer record lists 126 trainer files. Against pinned source `48776fba8af26b16b7e6813def7ccf571f56c1ac`, the only file hash difference is `src/wnn/training_dynamics.py`; all input, feature, model, prediction-input, and tied-lead files match. For both TLeads, all seven recorded input implementation hashes match the pinned source. The FBC record has no separate `input_feature_schema`, but its trainer-file inventory covers the same inference/input modules and those hashes match. The single difference is consistent with the strict optimizer-factory correction, which is outside inference/input code.
- **Fixed evaluation comparison and planned controls.** [`grade_teacher.py`](grade_teacher.py) fixes the pool at FBC `.34`, TLead-S5 `.33`, TLead-S6 `.33` (sum `1.00`), pins the full-valid target cache, and compares with `tt29rep_fbc1k_s5`. The allocation freezes alpha `.9`, epoch 3, seeds 3/5, a new seed-5 single-teacher control, and the exact reused `q14s_local_kd90_s3` control. These are adequate controls for the stated pool-replacement screen; they do not isolate “diversity” as a causal mechanism, which the packet already acknowledges.

## Required pre-fit target check

In [`datasets.py`](../../../../src/wnn/training/datasets.py), teacher targets are built as `sum(scale * prediction) / len(teachers)`; [`data_caches.py`](../../../../src/wnn/training/data_caches.py) parses `name*scale` without normalizing the scales. Therefore direct entries `q14t_fbc_s5*0.34,q14t_tlead_s5*0.33,q14t_tlead_s6*0.33` produce `(0.34 FBC + 0.33 TLead5 + 0.33 TLead6) / 3`, not the frozen pool. With the current implementation, equivalent direct scales are `1.02, 0.99, 0.99`, or the safer route is a preweighted target cache containing the exact mixture.

Before any student fit, freeze and check the actual train-target artifact: source=`train` only; row-group order equal to the split’s train target order; sidecars bind all three imported checkpoint/provenance hashes; and target values equal `0.34*FBC + 0.33*TLead5 + 0.33*TLead6` within the declared FP32 accumulation tolerance. Also verify the `.9` label/teacher blend is applied once by the student loss, after this pool is formed. Record the target/cache hash and effective weights in the run config. This is a small deterministic cache check, not a new scientific fit.

The in-flight full-valid pool grade and the allocation’s resource/reserve re-admission remain separate launch gates. Passing the target construction check would establish recipe correctness only; it would not validate the pool’s quality or authorize fitting by itself.
