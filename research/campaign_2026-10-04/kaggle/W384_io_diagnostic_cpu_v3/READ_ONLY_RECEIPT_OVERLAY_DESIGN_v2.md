## Prototype boundary

`receipt_overlay/receipt_overlay.py` implements an isolated adapter. It does not change shared verifiers, frozen worker code, source datasets, or production training/scoring. It accepts a root manifest bound to an exact kernel slug and provider dataset versions, and it checks its own source SHA against that manifest. The root manifest separately pins the existing bundle/registry identities, verifier source hashes, and full expected path/SHA/size descriptors. These claims are not treated as proof that file content was read.

At runtime, the prototype resolves each unique descriptor under its provider mount, opens it read-only without following the final symlink, checks the externally pinned provider-version map and read-only mount identity, records pre-read path/FD identity, reads the entire content through the held FD to SHA-256, and compares against the expected digest. It repeats the path/FD and mount checks after reading. It then seals a canonical receipt in a Linux memfd and retains all source FDs for the process tree. A child can reuse a digest only when the sealed receipt, exact kernel/version binding, held read-only FD, current path resolution/stat, mount identity/read-only state, and alias identity still match. Otherwise it computes a new strict full hash or fails closed. Receipt reuse is scoped to one exact kernel process tree and is not portable across runs. W384-v3's worker did not independently expose dataset version markers; the proposal pins exact versions from the reviewed provider inventory in the root manifest and kernel attachment metadata, while the required full content hash remains authoritative.

## Safety and decision gate

The current source-level prototype still needs a separate root review, then a bounded private CPU-only provider exercise on the exact three existing READY datasets before any GPU use is considered. That exercise must independently prove actual provider dataset versions, mount read-only state, retained descriptor identities across child use, full initial hash completion, strict-hash fallback for every invalidation, and resource bounds. If any condition cannot be observed, retain strict duplicate hashing. A receipt may never be reused across kernel runs or treated as a substitute for a fresh initial content read.
