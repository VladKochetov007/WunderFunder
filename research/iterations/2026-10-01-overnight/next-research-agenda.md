**1. Reuse one prefetch stream across epochs — test a resource mechanism, without changing learning.**

Observed source: [CudaPrefetcher](training/train_aux.py) creates a CUDA stream in its constructor (line186), and the epoch loop constructs a new prefetcher (line857). Root separately reported control GPU usage around3591→4455→5319→3875MiB across epochs and a sampled peak as high as5617MiB against the5632MiB cap. Both controls completed successfully. Those measurements do **not** distinguish live tensors from cached allocations, establish a leak, or prove stream causation. PyTorch documents that unused allocator reservations remain visible in nvidia-smi, and distinguishes allocated from reserved memory; side-stream synchronization and tensor lifetime tracking must remain correct. [Official CUDA semantics](https://docs.pytorch.org/docs/2.10/notes/cuda.html#memory-management).

Hypothesis: successive stream identities prevent useful reuse of similarly sized prefetch allocation blocks, increasing reservations near the cap. Treatment: construct the existing prefetcher once outside the epoch loop, retaining its current `__iter__`, loader iteration count, `wait_stream` and `record_stream` behavior. Control: current per-epoch construction. This is unrelated to failed auxiliary/optimizer treatments and adds no serving work.

Cheap falsifier: two fixed generated four-epoch runs, identical pinned batch shapes and consumer work, fresh process per arm, one GPU, ≤120s/arm and5632MiB. Record actual stream IDs, allocated/reserved/current/peak bytes, inactive-split bytes, driver-visible usage and batch lifetimes at identical points. Do not insert per-batch synchronization or `empty_cache`, which would change the mechanism. Require identical batch/RNG traces and generated model/gradient/update checks. Close this narrow claim if reservation growth is absent, survives stream reuse, or reflects equally growing live tensors. A prospective practical spending threshold is ≥512MiB reduction in peak reserved memory without new waits or >3% wall regression; that is an engineering gate, not a statistical claim.

What changes the decision: reproducible reservation reduction plus exact computational checks justifies a future trainer maintenance change; a target-free pilot followed by one matched ordinary control is enough to verify its effect. It needs no WP search. Main risk is a use-after-free/race introduced while reorganizing stream lifetime, so retain the existing dependency calls and test epoch boundaries. Tonight's immutable training contract and currently successful jobs make an automatic patch inappropriate.

**2. Refresh the carried student state after parameter updates — first test whether the mismatch matters.**

The trainer computes and detaches chunk state at lines949–955, then updates model parameters at lines1083–1085 and carries that state into the next chunk. Thus state and parameters belong to different update instants. For chunk input `X_b` and incoming state `s_b`, the current loop carries `h_b = F(theta_b, X_b, s_b)` after changing weights to `theta_(b+1)`. The proposed treatment carries `stopgrad(F(theta_(b+1), X_b, s_b))` instead: one no-gradient replay of the just-completed chunk. It is only a local refresh; the incoming `s_b` can still encode older parameters, so this is not an exact full-prefix reconstruction.

This is distinct from SAM's perturbed loss surface: its [frozen spec](sam/spec.md) deliberately retained the first unperturbed forward's state. It also differs from periodic inference resets, already-negative warm-up/position arguments, changing chunk2000 to chunk500, or adding CTX memory. There is no new state, feature, horizon or reset at inference. R2D2 studied parameter lag and recurrent-state staleness in replay-based reinforcement learning; it motivates this diagnostic, **not** an expectation of benefit in this supervised one-update-lag regime. [Primary paper](https://openreview.net/references/pdf?id=Hy7PKCFCQ).

Matched control: perform the same post-update no-gradient replay but discard its state; the candidate retains it. Keep the full parent objective, data order, chunk2000, dropout0, AMP, clipping, optimizer/scheduler and EMA updates identical. Leave EMA-teacher state handling unchanged in both arms. No extra optimizer or EMA update occurs. A skipped GradScaler update retains the original carried state. First prove zero-learning-rate/skip parity, unchanged RNG/buffers, causal prefix/reset behavior, and absence of gradient flow through the replay.

Cheap falsifier, separately allocated next session: one ordinary-parent diagnostic pilot capped at256 optimizer attempts/480s, on fixed train-only chains, with16 predetermined probe boundaries. This is one counted diagnostic training run, not a free unlogged fit. At each boundary, freeze current weights and compare next128-row outputs from (a) stale state, (b) locally refreshed state, and (c) current-weight replay of the entire available prefix. Probe calculations use only the causal raw prefix and no validation labels. Normalize output discrepancies by reference RMS with a fixed numerical floor. Decline a full study unless the median stale/reference discrepancy is at least1% and refresh reduces it by at least50% in12/16 probes. A small discrepancy closes this spending proposal, not every possible training phase; the short pilot may miss later learning-rate behavior. A large discrepancy is still **not** evidence of improved prediction.

Only if that falsifier passes: preregister two paired seeds, folds0/1, ordinary parent4/ep3 then H2 two epochs/ep1, with one fixed ensemble slot/composition and no epoch/blend search. That is16 forecast fits, roughly1–2hours on the current two GPU lanes plus validation/export reserve, subject to measured pilot cost. Count every attempt. Serving shape and cost stay unchanged. Promote only a prespecified practically useful ensemble gain with consistent paired signs; report seed variation separately from chain uncertainty. Risks: extra forward cost, AMP skip semantics, implicit buffer mutation, and regularization from stale states possibly being helpful. No late-night automatic launch: the mismatch's magnitude is unknown, the current campaign has already spent most of its fit budget, and the replay changes training semantics despite leaving serving unchanged.

**3. Separate AVX2 capability from F16C availability before optimizing another kernel.**

The [full v3 audit](final-runtime-audit/outcome.md) projected43.36min for callbacks and45.40min for the complete process. The [fixed fallback traces](final-runtime-fallback-isa/outcome.md) projected83.38min for AVX2 and105.37min for v2. These were different compiled paths on the same host, not measurements of three physical CPU models.

Source explains an important confound: `critic/native_order_v2/build.sh` compiles AVX2 with `-march=x86-64-v2 -mavx2 -mfma`, omitting `-mf16c`. A source-only empty-input GCC macro inspection on CPU37 confirmed `__AVX2__=true`, `__FMA__=true`, `__F16C__=false`; it compiled no executable and ran no benchmark. `kernels.hpp` enables half-weight storage only when **F16C AND AVX2 AND FMA** are defined. Therefore the wrapper's existing `half_weights=True` request is ignored by the AVX2 module; dense matrices use FP32. Its v3 counterpart uses stored FP16 weights with FP32 products/sums. The measured ratio is not a clean estimate of AVX2 arithmetic inefficiency, and source alone does not establish a cache-bandwidth bottleneck. GCC exposes these instruction switches separately and warns that enabled ISA instructions constrain compatible processors. [GCC13.3 x86 options](https://gcc.gnu.org/onlinedocs/gcc-13.3.0/gcc/x86-Options.html).

Conditional mechanism: an additional narrowly compiled `avx2_f16c` profile using the existing half-weight operator, dispatched only after verifying its actual CPU/OS prerequisites, even when unrelated full-v3 flags are absent. Keep the genuine no-F16C fallback. This is not another INT8 quantizer, VNNI tile/packing sweep, or restoration of the closed Q3 composition. It cannot speed up a CPU genuinely lacking F16C, and may benefit no relevant evaluator hardware at all.

First falsifier is capability relevance: establish an actual allowed deployment profile that has AVX2/FMA/F16C but fails the current v3 selector; if none is relevant, spend nothing. Then one fixed build, static instruction audit, generated dispatch truth table and adversarial numerical/reset tests. Compare its complete outputs against the existing v3 FP16 operator, not against old AVX2 FP32 and a claim of unchanged numerics. Only after parity review, allocate one target-free matched callback pair and a long full-harness check; preserve both failures and noise, no ISA/compiler sweep. A prospective useful result is correct dispatch plus callback≤50min/full-process≤60min on that actual profile. Budget: a few CPU minutes for build/synthetic checks; long audit about45–60min only if warranted. No forecast fit or WP query is needed if exact existing numerical behavior is established.

Decision risk: adding an unsupported instruction can crash the package; changing summation order may alter recurrence. A forced flag mask on the current host cannot establish safe operation or speed on another CPU. Current v3 qualification already exists, while unknown host capabilities and failed true fallback timing require an explicit limitation. That uncertainty did not authorize modifying the ready ZIP tonight.

The first two items have the best next-session value: stream reuse is cheap and can improve resource headroom without a forecasting claim; state refresh is the sole new forecasting mechanism here and has a direct rejection test before expensive fits. The ISA profile is conditional engineering insurance. None reopens a failed gate or supplies fresh hidden-test evidence.
