# Exact-order runtime handoff — 2026-10-01 01:11 UTC

Frozen source: `native_order/`. Only the `Ensemble` implementation differs from the frozen feature-capable native source: alternate deterministic forward/reverse member execution and retain the original member-index summation order. Keep the largest hidden model away from the endpoints when smaller models exist, which lets a small member run twice consecutively across a row boundary. Sequence reset restores the initial order. There is no model, feature, precision, or clock-dependent membership change.

On beleriand Xeon Gold 6230, CPU22, one thread, scorer-image Python3.11, five actual input sequences (100,000 rows), alternating independent processes: fixed three h128 members improved from mean77.13 to68.95 µs/row (10.60%; projected45.28minutes for39.4million rows). Mixed fixed four improved only158.47 to154.54 µs/row (2.48%; projected101.48minutes). Complete row callbacks, feature calculations, and Python/native crossings are included. CPUtime≈walltime. These are host projections, not public-runtime guarantees; recorded public41m42s cannot be reconciled with identical local hardware evidence. Three members fit this host's budget with useful margin; four still do not.

All100,000 prediction rows, including warmup, are byte-identical between original and changed v3. Portable v2 and AVX2 binaries also match their respective original binaries on10,000 rows. Separate member-sum, reset, prefix/future-mutation, chunked-run, and permutation tests pass allthree ISAs. Cross-ISA outputs need not match because the original fallback arithmetic differs. Portable fallback timings are slower and do not establish budget compliance. Exact source and raw receipts are hashed in `order-freeze.json`; summarized receipts are in `order-summary.json`. Independent review/reproduction by critic_delivery is pending.

The first independent Python sum oracle incorrectly used separate multiply and add for v3/AVX2, producing up to2.38e-7 difference at coefficients1/3; this failed harness and explanation remain archived. Matching the original engine's FMA with libm fmaf resolved it without changing engine code or relaxing parity.

Other probes were negative: expanded fp32 copies of fp16 weights nearly doubled kernel time; eight-row AVX2 kernels were slower; scoped denormal flushing preserved outputs but did not improve runtime. Explicit512-bit same-order FMA was noisy and showed no reliable benefit. Runtime decomposition assigns the main cost to dense recurrent matrices and cache working sets, especially hidden256; Python crossings and scheduler waits are small. No target arrays, WP scores, calibration, or training were used for this systems audit.
