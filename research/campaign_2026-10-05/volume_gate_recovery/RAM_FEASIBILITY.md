# E427 local RAM feasibility (static audit; no allocation or fit)

## Decision

A 23 GiB worker cap is not justified by the available measurements with the required 1 GiB peak margin. The closest successful same-parent fit already reached 25,756,786,688 bytes (23.98 GiB) under a 24 GiB worker cap, leaving only 13,017,088 bytes (12.4 MiB) of recorded headroom. E427’s current draft asks the loader for a larger worker/prefetch envelope than that historical fit. The fixed local 24 GiB request is also arithmetically inadmissible with the unchanged support reserve: 24 GiB + 4 GiB = 30,064,771,072 bytes, 64,771,072 bytes above the actual 30,000,000,000-byte parent hard limit before existing usage.

Do not change the sealed worker limit to 23 GiB on this evidence. A one-worker data-loader profile could reduce the anonymous batch-queue envelope, but its optimistic estimate misses 23 GiB by about 126 MiB against the measured parent peak before accounting for implementation variation; it has no proven 1 GiB safety margin. A remote/larger memory placement or a separately reviewed streaming/worker-profile design with a representative measured peak is needed before a fit can be admitted. The existing CPU/GPU guards, 24 GiB reservation, and all three scientific arms remain unchanged by this audit.

## What the trainer holds

`Sequences` keeps row-group indices, opens `SequenceFile` lazily, and memory-maps teacher/propensity arrays. It does not construct a whole train-set feature tensor in Python. Each `SequenceFile.read` asks PyArrow for one 20,000-row group and 112 feature columns, then stacks those features into a contiguous float32 array; targets, scoring mask, and propensity are added per sequence. This keeps the main working set to the current batch plus loader queues, worker decode temporaries, model/checkpoint state, and file-backed cache pages.

For the fixed E427 fit batch (32), 20,000 rows, 112 float32 features, four float32 target channels (two labels plus the mean of the two teacher outputs), a bool scoring mask, and one float32 propensity value, the returned loader payload is:

`32 × 20,000 × ((112 + 4) × 4 + 1 + 4) = 300,160,000 bytes` (286.3 MiB per batch).

The fit draft sets `WNN_LOADER_RAM_GB=6`, enables `--fast` (which turns on pinned memory and propensity caching), and omits `WNN_LOADER_WORKERS`. The worker environment sets `WNN_THREADS=8`; the loader helper therefore permits four workers. Six GiB / 300,160,000 gives capacity 21, so `dataloader_budget` selects four workers and prefetch 2. Its stated accounting includes queued batches plus one consumed and one pinned/in-flight copy: up to `(4 × 2 + 2) × 300,160,000 = 3,001,600,000 bytes` of returned-batch payload, before PyArrow decode/stack temporaries and worker-process overhead.

By comparison, the successful parent fit explicitly set `WNN_LOADER_WORKERS=2` and a 3 GiB loader budget. The capacity was still sufficient for two workers with prefetch 2, or six payload batches: 1,800,960,000 bytes. E427’s current declared loader configuration therefore has a nominal 1,200,640,000-byte larger queue envelope than the parent receipt. E427’s `--no-eval-during-fit` removes the synchronous holdout loader, but the parent’s holdout batch size is 16 and that one current batch is only about 146 MiB. That difference does not establish a 1 GiB fit margin.

The E427 volume28 feature is computed from `inputs` after the batch has been copied to CUDA; its `[32, 20,000, 28]` context and recurrent activations primarily affect VRAM, not host tensor residency. The E427 gate adds only about 6.4k allocated parameters, negligible beside parent/checkpoint state. This makes the larger host loader queue, not the new parameter block, the most visible host-RAM delta from the recipe as drafted. The exact forward path, PyArrow allocator reuse, pinned-memory overlap, and kernel file-cache high-water remain unmeasured for this E427 continuation.

The cached inputs are large but not all copied into anonymous memory. The declared training and validation Parquet files are 29,240,219,011 and 5,615,509,128 bytes. The two train teacher arrays are 1,696,960,128 bytes each; the two validation teacher arrays are 299,680,128 bytes each. Propensity caches are 848,560,128 bytes (train) and 149,840,128 bytes (validation). The trainer opens these arrays with `mmap_mode="r"`; pages become file-backed cache as accessed and may be reclaimed. Exact input `POSIX_FADV_DONTNEED` before admission is only a cache hint: it can remove existing clean cache but the fit will repopulate pages as it reads row groups. It cannot be counted as a 1 GiB peak reduction.

## Measurement and admission arithmetic

The closest successful historical receipt is `e412-combo-final-s3-v2`, run name `c20261004_combo_s3_final_r1`, the exact epoch-3 parent for E427. It completed with exit 0 and explicit final OOM, OOM-kill, and group-kill counters all zero. It used batch 32, chunk 1,000, train+valid/full-valid, the same two cached distillation teachers, propensity cache, auxiliary next/structure objectives, Muon, and EMA. It ran four epochs rather than E427’s one, and it evaluated holdout at epoch end. Its measured peak was 25,756,786,688 bytes RAM and 4,451,205,120 bytes observed VRAM with a 25,769,803,776-byte RAM cap and 4.2/4.8 GB GPU allocator/stop thresholds. This is a useful same-parent receipt, but it is not an E427 arm receipt and its historical queue-worker count was two, not four.

The 23 GiB candidate’s queue arithmetic is not sufficient evidence to set that cap. If the E427 draft were changed to `WNN_LOADER_RAM_GB=1`, capacity would be 3, selecting one worker and prefetch 1 (three accounted payload batches, 900,480,000 bytes). Relative to the historical parent’s six-batch queue, that would save only 900,480,000 bytes. Subtracting that entire amount from the historical peak predicts 24,856,306,688 bytes, still 132,473,856 bytes over a 23 GiB cap and with no 1 GiB margin. This optimistic subtraction assumes the queue envelope fully accounted for the peak and every saved byte translates directly into peak reduction; neither assumption has been measured. No such environment change or cap change was made here.

## Residual risks and next evidence

The largest uncertainty is the combination of four DataLoader workers, pinned-memory/CUDA prefetch, and Parquet decode buffers. The E427 draft may raise anonymous queue residency by roughly 1.2 GB versus the parent fit before accounting for worker-private Arrow state. File-backed pages are reclaimable but can refill during the epoch. The historical cgroup peak receipt reports a scalar peak, not anon/file breakdown or a time-aligned peak trace, so it cannot distinguish queue pressure from resident model state or warm file cache. Parent validation also means the historical peak might include one extra synchronous 16-sequence batch; its exact contribution at the peak is unknown. These facts prevent a defensible lower-cap guarantee.

A two-batch smoke can detect gross startup failures but cannot establish the epoch’s file-cache/worker peak.
