## Checks performed

- E480 has no default seed. The CLI requires both registered seeds, in the order 271829 then 271830. `make_initial_state` explicitly seeds before constructing the E474 GELU baseline; synthetic tests confirm the 271829 state is bitwise equal to E474's seed receipt and repeated initializations for both seeds are deterministic. Each seed's NumPy fit permutation is computed once per cell traversal and reused across all 12 cells. The CPU receipt shows one shared first-B4 group order across all 12 cells for each seed, and the orders differ between seeds.
- The actor builds and verifies all 474 float64 learning-rate values before updates. It checks array equality and little-endian float64 SHA-256 against the frozen E476 trace receipt. Current E476 LR-trace SHA-256 is `046f38f67792af73450bbbb958403834d948495e4ba64b263a2a9a2ff935e4ff`; current E476 trainer SHA-256 is `5acc0efa8295338b39ffc0a0c9412484daec277967d8dc2e161affee1d1786e6`. E474, E470, optimizer, and model dependency hashes also match the identities recorded by the CPU v3 source receipt.
- The training path uses the two unchanged E474 activation variants, 61,058 parameters, E470's fit-only cohort/loss, the registered constant/warm-cosine/constant-mean traces, common seed-specific initial weights, the same per-seed fit order, and 474 updates (6 B4 batches × 79 carried-state chunks). It detaches state between chunks and resets it at the start of each B4 batch. Muon selects exactly the four two-layer GRU matrices with three gate blocks; all other parameters use AdamW. Every optimizer group receives the same per-step LR.

- Ruff format/check, `py_compile`, the bounded synthetic CPU invariants, and clean-directory `--help` passed. ## Probe binding condition

The code compares recomputed schedule arrays to the contents and trace hashes in `preflight_cpu_v5/lr_traces.json`, and the v3 manifest records the current file hash. It does not itself assert a literal expected SHA-256 for that receipt (or literal expected hashes for every inherited source); the expected E476 trace hash is documented in `SOURCE_RECEIPT.md`. Before launching the CUDA probe, the root's content-bound spec should pin the actor, tests, design, E470/E474/E476 sources, optimizer/model implementation, cohort, dataset, and E476 trace receipt to the exact hashes in `SOURCE_RECEIPT.md` and `preflight_cpu_v3/fit_manifest.json`. This is a seal requirement, not a reason to alter the registered recipe.

The actual-device probe should be limited to the 24 prescribed B4×256 updates, verify the per-cell finite/update receipts and CUDA peaks, and stop on any source/data identity mismatch. A passing probe would not establish full-fit runtime or peak memory; those still need the root's worker limits and monitoring for any later fit admission.
