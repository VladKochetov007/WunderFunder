## Memory path traced from the sealed trainer

Each training sample reads one 20,000-row Parquet row group. `SequenceFile.read` asks PyArrow for all 112 feature columns, stacks them into a contiguous float32 matrix, and adds targets/mask; `Sequences` separately reads the cached teacher and propensity arrays with `mmap_mode="r"`. The train Parquet input is 29,240,219,011 bytes and the worker reports 10,607 training sequences; batches are shuffled and revisited for four epochs. Thus the worker streams a broad section of the mounted Parquet corpus and creates per-batch Arrow decode/stack temporaries. The same inputs are read concurrently by two independent training process trees, while clean file pages may be shared and reclaimed by the host.

For batch 32, the returned payload is `32 * 20,000 * ((112 + 4) * 4 + 1 + 4) = 300,160,000` bytes: 112 float32 features, four float32 target channels (two labels plus the averaged two-teacher output), one bool score mask, and one float32 propensity. The spec sets `WNN_LOADER_RAM_GB=3` and `WNN_LOADER_WORKERS=1`; `dataloader_budget` selects one worker with prefetch 2. Its documented budget accounts for queued batches plus a consumed batch and a pinned/in-flight copy (up to four batch payloads, about 1.20 GB), before Arrow decode/stack temporaries, IPC/pinning, model and optimizer state, and file-backed pages. The trainer was already at one DataLoader worker, so merely changing `WNN_LOADER_WORKERS=1` is not a fix. Reducing loader budget to 1 GiB would select prefetch 1 and save at most one returned batch (about 300 MB) under this accounting.

A whole-dataset decoded feature cache is not a practical remedy: at 10,607 sequences, 20,000 rows, 112 float32 columns, it would require about 950 GB before auxiliaries. Existing teacher/propensity caches are mmap-backed and are already shared at the OS page-cache level. The exact 3.1-GiB probe-to-fit RSS growth cannot be apportioned between DataLoader/pinned batches, Arrow allocator retention/fragmentation, runtime state, or other private pages because v7 sampled only summed process-tree RSS. It is plausible that continued row-group decoding and file-cache refill contributed to host pressure, but v7 does not prove which component dominated. `POSIX_FADV_DONTNEED` is only a clean-cache hint: its successful pre-fit advice does not prevent files from being reread or cache pages from repopulating.

## Bounded v8 design for review (not implemented)

Keep the sealed widths, seeds, plans, data/checkpoint hashes, batch 32, shuffled four-epoch order, optimizer/scheduler, loss, masks, precision, and checkpoint/score rules byte-identical. First test a transport-only loader profile that sets `WNN_LOADER_WORKERS=0` (or one worker with the 1-GiB budget/prefetch 1) to reduce queued copies; do not claim that this alone controls PyArrow allocator or host page-cache growth. A bounded CPU check using a 10,607-item deterministic dataset with seed 3 produced the same 10,592 shuffled/dropped-last indices for DataLoader workers 0 and 1; this supports order parity, but a source-bound test should use the actual trainer sampler before sealing the candidate.

Prefer retaining both-GPU overlap only if a full resource-only profile shows the revised workers stay within the current per-worker RSS limits and host reserves. Instrument each worker's parent/child RSS separately and collect time-aligned `MemAvailable`, cgroup `memory.current`/`memory.stat` anon+file, and GPU bytes at the existing watchdog cadence. Add a fail-closed runtime host-availability stop at the existing 20% host reserve; keep the existing admission rule and GPU thresholds. A fresh one-batch probe cannot establish the four-epoch memory envelope.

If a serial fit phase is considered to reduce the two concurrent Arrow/loader working sets, it must be split into two distinct runner invocations, bind each width to the physical T4 used by that width's successful probe, advise only its declared input files before admission, and re-run the exact host-resource gate before starting the next fit. The current runner/phase controller assumes a paired concurrency-two fit phase, so this would require a new reviewed controller path. Two sequential full fits also risk exceeding the unchanged 25,180-second whole-job/12,600-second per-worker limits; derive a credible runtime estimate before building or sealing that path. Do not solve the measured failure by blindly doubling reservations or by marking either fit complete.

The most useful next measurement is a controlled, same-data resource-only profile of the exact fit recipe with one width and `WNN_LOADER_WORKERS=0`, capturing parent-versus-child and anon-versus-file memory. That distinguishes whether eliminating the DataLoader child/queue provides enough margin to keep the original paired schedule and host guard. If not, evaluate the reviewed sequential controller only after its wall-time and resource admission are shown feasible. No v8 bundle or spec was created because neither option has a measured full-run resource envelope yet.
