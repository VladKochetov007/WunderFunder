## W384 v5 failed after its probes, before either fit

The current Kaggle state for `vladkochetov07/wnn-w384-fold1-dualt4-20261004-v5-runner`
is `KernelWorkerStatus.ERROR`; the provider `failure_message` is blank. The

- W256 probe: one completed batch / 10 optimizer completions; peak sampled GPU
  memory 3.27 GiB and worker RSS 4.95 GiB.
- W384 probe: one completed batch / 10 optimizer completions; peak sampled GPU
  memory 3.86 GiB and worker RSS 5.11 GiB.

The phase then failed at fit admission. The bounded [provider kernel
log](W384_v5/provider_output/wnn-w384-fold1-dualt4-20261004-v5-runner.log)
ends with the underlying error from
`scripts/kaggle_gpu_runner.py:87`:

```text
ValueError: Worker reservation exceeds host operational budget
```

Each fit spec reserves 10 GiB RAM and 2 CPUs. The runner computes a current
host budget as `min(0.8 * host_capacity, host_available - 0.2 * host_capacity)`
and rejects any individual spec whose RAM reservation exceeds that value.
This check occurs before the runner decides whether to reduce concurrency, so
changing the job to one worker alone would not address an over-budget
individual spec. The exact host-capacity/available-memory snapshot at the fit
admission point was not recorded; the receipt therefore proves the comparison
failed but not the exact byte threshold. No full fit worker, checkpoint,
prediction, or score was produced.

The prepared v5 receipt confirms the immutable scientific archive and mount
manifest were the reviewed ones. The failure is a fresh host-memory admission
issue, not the earlier mount-guard defect and not an OOM. Before considering
another admitted version, record host capacity, available memory, and computed
budget immediately before fit admission, then set a per-worker RAM reservation
that is both below that budget and still safely above measured fit RSS. The
runner can then serialize the two workers if their combined reservation does
not fit. Do not infer that the probe RSS is itself a safe full-fit cap.
