Verdict: KEEP UNAPPLIED PROTOTYPE. Two material issues need controller correction

FAIL 1 — antithetic arm changes normalization, not just training order.
Location: opt2/trainer_candidate.py:1156-1157 (same hunk in trainer.patch),
sampling.py EpochOrderSampler.__iter__, live scripts/train_rnn.py:488-499.
The antithetic sampler remains reversed at epoch -1. The comment claiming the
normalization pass is the same for the paired control is false. fit_normalization
uses only two batches, and additionally subsamples flattened features every 7
rows. Reversing the complete order therefore changes normalization membership
and can change subsampling even if all normalization sequences fit in two batches.
This survives divisible dataset sizes; accounting for drop_last tails does not
resolve it. PLAN rank8's order-only mechanism is confounded by input scaling.
New CPU reproduction executes the actual live normalization function extracted
by AST, with identity feature construction on synthetic scalar inputs only:
64 sequences, batch8, 7 timesteps, seed3, normalization epoch -1, no dropped tail.
Control mean/std = 30.4375 / 19.273363; antithetic = 35.5625 / 12.732995.
The reproduction test passes by asserting the demonstrated mismatch; PASS of
the test is evidence of this implementation FAIL, not evidence of arm correctness.
Fix: use an identical non-reversed normalization sampler in both arms, then
enable reversal only for training epochs. Require normalization_identity hashes
to match; preserve separate accounting of dropped training membership. A shared
normalization checkpoint can also isolate this, but is not the current fresh-fit
proposal. No trainer edits were made by this reviewer.

FAIL 2 — PLAN's literal launch helper is not an admitted controller proposal.
Location: opt2/PLAN.txt:22-28. The helper directly invokes scripts/limited and
dcurve_fold.sh. A per-process CPU/RAM cap does not implement campaign_job's GPU
serialization, observed-device-memory cap, admission barriers or family slice.
The surrounding prose requires controller admission, but the literal executable
helper relies on unspecified ambient state and never calls continuation/run_gpu.sh.
If run independently, it bypasses the required admission; if nested in an existing
controller scope, another scripts/limited wrapper can create a sibling scope or
reuse inherited scope-unit settings. Do not accept it as ready to queue.
Fix the proposal into one serialized controller GPU queue job per fold/arm, whose
payload uses the existing wrapper, e.g.:
  research/campaign_2026-10-03/continuation/run_gpu.sh timeout 4800 bash research/campaign_2026-10-01/jobs/dcurve_fold.sh 0 opt2_m2a75 3 --optim muon --optim-switch 0.75:adamw --grad-stats
This is a PAYLOAD for the controller's campaign_job GPU admission/monitor, NOT
an independently authorized shell launch. The controller supplies its family
slice and one observed VRAM cap; do not add independent scripts/limited sibling
launches or use allocator fractions as an observed-memory guarantee. No GPU job,
queue edit, service change or device inspection was performed in this review.

Adam->Adam, Muon->Muon, Adam->Muon, Muon->Adam; hidden Muon scope and head lr .25.

parameters and absence of frozen optimizer state; finite continued fitting;

Unchanged-rule switches retain seven states and are bit-identical to matched

No optimizer-state/scheduler-age failure was observed. Source inspection confirms
Adam moments/step ages survive unchanged rules, matrix rule changes cold-start,
current lr/betas/group scheduler metadata survive without scheduler reconstruction.
The second test does not independently prove equivalence of rule-changing
trajectories to another implementation or full GPU behavior.
AMP skipped attempts advance scheduler, switch clock and EMA in the live trainer;
this is inherited behavior, explicitly disclosed in FLAGS, not a new opt2 bug.
Switch-before-zero_grad/backward/unscale avoids stale GradScaler optimizer flags.
