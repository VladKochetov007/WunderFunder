# Optimizer families for the recurrent screen

**Literature scout, 2026-10-08.** Prepared in the isolated `research/gru512-768-capacity-20261008` worktree by the assigned Codex **GPT-6 Luna, max-reasoning** actor. Sources were searched and read through the web research tool; links below go to primary papers or author-maintained implementations. This is a source-grounded proposal, not an experiment: no model fit, data read, provider action, score, or numerical prior was produced.

## Recommendation

Keep the current seed-9 capacity packet small and interpretable: (1) width-512 AdamW control, (2) width-512 Muon-on-recurrent-gate-matrices with AdamW for the remaining parameters, and (3) width-768 with the same Muon/AdamW split. The first pair tests an optimizer intervention at one width; the second pair tests width under that hybrid optimizer. This is not a factorial design and cannot estimate an optimizer-by-width interaction. It is a useful three-arm screen before additional seeds or an endpoint blend.

If a later allocation supports two follow-ups, prioritize (4) one width-512 RAdam arm as a low-engineering adaptive-optimizer contrast and (5) one width-512 NorMuon arm only if measured Muon updates show substantial neuron-to-neuron row-norm imbalance. Those are new recipes and need their own source review and authorization. Do not add them to the already frozen three-arm packet.

The current implementation maps the 211 input features through `inp: 211→H`, then a two-layer GRU and an output head. With `muon_scope=rnn`, `muon_param_groups` sends both `weight_ih_l*` and `weight_hh_l*` packed GRU matrices to Muon, splits each into three gate blocks, and leaves the input projection, readout layers and biases on AdamW. Thus this is a matrix-optimizer intervention on the recurrent core, not “Muon for every layer.” The implementation applies five quintic Newton–Schulz steps per update, decoupled weight decay, and an explicit update-RMS scale. Its orthogonalization precision is now governed by the explicit `native_bf16_if_supported_else_fp32_v1` policy: native CUDA BF16 only when compute capability major is at least 8 and PyTorch reports BF16 support, otherwise FP32. The trainer’s FP16 autocast/GradScaler is a separate precision path. See the frozen source in [`src/wnn/optim.py`](../../../../src/wnn/optim.py) and `src/wnn/training_dynamics.py` in the packet’s own source archive.

**Hardware gate:** the previous E540 worker reported a Tesla T4 (compute capability 7.5). The updated policy therefore selects FP32 for Muon orthogonalization on that device; it does not silently substitute a dtype because this fallback is explicit in the versioned policy and recipe. Before fitting, the actual device profile must execute the real gate-matrix optimizer step and record device capability, `torch.cuda.is_bf16_supported()`, and the selected orthogonalization dtype. Treat any mismatch between the declared policy and runtime metadata as a hardware/implementation failure, not a negative Muon result. [NVIDIA CUDA compute-capability table](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/compute-capabilities.html), [PyTorch BF16 support check](https://docs.pytorch.org/docs/stable/generated/torch.cuda.is_bf16_supported.html).

The three arms should preserve the frozen full-causal 211-feature view, clean fold-0 fitting membership, clip-2 weighted MSE objective, four epochs/fixed epoch 3, seed-9 explicit shared epoch sampler, and one selected hardware batch. Compare same actual attempted/completed/skipped update counts, finite parameter/gradient/loss evidence, and fixed-fold predictions. The packet’s hardware-only B8→B4 selection rule must run before score access. Profile actual peak GPU and host memory and wall time; width-768 has roughly quadratic recurrent-state/compute growth, and Muon adds per-step matrix products. No literature result licenses a guessed speedup or a width-independent memory forecast.

## Source cards

| Family and primary source | Mechanism and correspondence to this GRU | Cost, state, and limitation here |
|---|---|---|
| **Adam / AdamW** — [Adam](https://arxiv.org/abs/1412.6980); [Decoupled Weight Decay Regularization](https://arxiv.org/abs/1711.05101) | Coordinate-wise first/second moments are the necessary anchor. AdamW decouples shrinkage from the adaptive gradient update. Current recipe already uses AdamW for the full model and as the non-Muon half of the hybrid. | Two FP32 moment tensors per parameter plus ordinary model/gradient memory. Low implementation risk; per-step work is elementwise. Keep exact trainer defaults and schedule in the control. A single seed estimates a screen, not tuned optimizer superiority. |
| **AdaBelief / RAdam** — [AdaBelief](https://arxiv.org/abs/2010.07468), [author implementation](https://github.com/juntang-zhuang/Adabelief-Optimizer); [RAdam](https://arxiv.org/abs/1908.03265), [PyTorch API](https://docs.pytorch.org/docs/stable/generated/torch.optim.radam.RAdam_class.html) | AdaBelief scales by the EMA of gradient prediction error, adapting to whether observed gradients match the moving-average direction; this could matter for noisy, heterogeneous target gradients. RAdam rectifies early adaptive-step variance. Both are direct, separable alternatives to coordinate-wise AdamW. | Adam-like two-tensor state and small elementwise overhead. RAdam is the cheaper first implementation contrast; the current OneCycle warm-up may already address part of RAdam’s early-step concern, so freeze schedule and interpret narrowly. AdaBelief defaults/epsilon/decoupled-decay options differ among implementations; independently implement the paper equation and specify them before use. They apply naturally to all parameters, but changing all groups is a broader intervention than current gate-only Muon. |
| **Adafactor** — [Adaptive Learning Rates with Sublinear Memory Cost](https://arxiv.org/abs/1804.04235) | Factorizes a matrix’s squared-gradient accumulator into row and column statistics. GRU gate blocks are explicit matrices, so factoring each gate block is structurally appropriate; the input/readout projections are also matrices. | Reduces second-moment state from O(mn) to O(m+n) for a matrix (momentum may add another state). However, this GRU is only millions of parameters; optimizer state may be much smaller than long-sequence activations and input staging. Defer unless profile shows optimizer-state VRAM is a meaningful bottleneck. Its update clipping, relative-step and parameter-scale settings must be separately frozen; this is not a drop-in AdamW replacement with otherwise identical numerics. |
| **Muon and matrix/polar variants** — original author’s [Muon design note](https://kellerjordan.github.io/posts/muon/); [Muon is Scalable for LLM Training](https://arxiv.org/abs/2502.16982) and [author implementation](https://github.com/MoonshotAI/Moonlight); [Practical Efficiency of Muon for Pretraining](https://arxiv.org/abs/2505.02222); [NorMuon](https://arxiv.org/abs/2510.05491) and [authors’ implementation](https://github.com/zichongli5/NorMuon); [Polar Express](https://arxiv.org/abs/2505.16932), ICLR 2026, and [author implementation](https://github.com/NoahAmsel/PolarExpress) | Muon applies an approximate polar/orthogonal factor to momentum matrices rather than coordinate-wise scaling. This aligns with packed GRU gate matrices, but the cited main evidence is transformer/LLM pretraining, not this sequence regression task. NorMuon adds a per-row second-moment normalization after orthogonalization; that directly maps to a gate’s output-neuron rows and is a plausible refinement if update norms remain imbalanced. Polar Express changes the polar-approximation polynomial/iteration method, i.e. the optimizer’s matrix subroutine rather than the objective or data. | Muon needs one momentum tensor for the matrix instead of Adam’s first and second moments, but costs iterative matrix multiplies each update. NorMuon adds O(rows) state per matrix. Polar Express stays matrix-product based and reports improved GPT-2 validation versus tested alternatives, but not GRU results. Current local implementation is quintic NS5 and its exact scale/scope must be preserved for the seed-9 comparison. First record actual optimizer time separately from train-step time. Do not combine NorMuon or Polar Express into V1/V2 silently. |
| **Norm-constrained LMO / Scion** — [Training Deep Learning Models with Norm-Constrained LMOs](https://arxiv.org/abs/2502.07529), ICML 2025; [author implementation](https://github.com/LIONS-EPFL/scion) | Chooses updates through a linear-minimization oracle over a selected norm ball. Spectral/operator geometry is related to Muon’s matrix geometry but defines a distinct update rule; the paper also discusses layer- and width-aware scaling. | The paper’s implementation can retain only weights and gradients, potentially attractive for larger widths. But it has norm choice, radius and LR as meaningful recipe parameters, and reported experiments focus on nanoGPT/MLP/CNN rather than this GRU. A follow-up would need one predeclared GRU gate-group norm and scale rule; do not borrow transformer radii. |
| **Shampoo / SOAP / SPlus / DASH / K-FAC** — [Shampoo](https://arxiv.org/abs/1802.09568); [K-FAC](https://arxiv.org/abs/1503.05671); [SOAP](https://arxiv.org/abs/2409.11321), [author implementation](https://github.com/nikhilvyas/SOAP); [SPlus](https://arxiv.org/abs/2506.07254), NeurIPS 2025, [author code](https://github.com/kvfrans/splus); [DASH](https://arxiv.org/abs/2602.02016), [author code](https://github.com/IST-DASLab/DASH) | These are curvature/covariance preconditioning families, not merely LR schedules. Shampoo uses matrix factors/inverse roots; SOAP runs Adam in a Shampoo eigenbasis; SPlus changes whitening stability/scaling and adds iterate averaging; DASH accelerates batched block preconditioning/inverse roots. K-FAC approximates Fisher blocks through Kronecker factors and has recurrent-specific extensions in the literature. | Typical Shampoo factors cost O(m²+n²) state per matrix and inverse-root/eigendecomposition work; SOAP retains Adam-like moments in rotated coordinates; SPlus reports 3mn+2(m²+n²) values for a dense matrix with its averaging/state scheme. DASH reduces implementation overhead but does not make curvature free. At H=512/768 and short sequences, factor update cost and extra checkpoint state may outweigh fewer steps. Keep as a later bounded arm only if Muon/AdamW profiles show optimizer compute is affordable and the scientific question warrants a curvature-family contrast. |
| **Lion / sign updates** — [Symbolic Discovery of Optimization Algorithms](https://arxiv.org/abs/2302.06675), [author implementation](https://github.com/google/automl/tree/master/lion) | Uses signed momentum direction and avoids coordinate-wise second moments. It transfers an unconventional simplification: scale-invariant sign steps may reduce state and regularize disparate gradient magnitudes. | Roughly one momentum state, but paper emphasizes lower LR and shows stronger gains at larger batch sizes for selected tasks; that does not establish benefit at our sequence batch. On weighted regression, sign updates can suppress useful magnitude information. Test later with LR tuning shared by a prespecified small protocol. |
| **SGD + momentum/Nesterov** — [On the importance of initialization and momentum in deep learning](https://arxiv.org/abs/1308.5359) | A low-state, norm-faithful direction is a useful non-adaptive reference. It tests whether per-coordinate adaptivity is doing essential work in the MSE problem. | One momentum buffer (or none), low update overhead, but likely more LR-sensitive under heterogeneous features/targets. Existing trainer’s SGD path has distinct constraints; hold the loss, clipping, sampler and schedule fixed and avoid using it as a cheap proxy for Muon. |
| **Schedule-free / Prodigy / D-Adaptation** — [The Road Less Scheduled](https://arxiv.org/abs/2405.15682), [official code](https://github.com/facebookresearch/schedule_free); [Prodigy](https://arxiv.org/abs/2306.06101) | These mostly address LR selection/scheduling, not the same update-geometry question: Schedule-Free changes the iterate averaging/parameterization and evaluation point; Prodigy estimates an effective LR scale. Treat as schedule/adaptive-step interactions, not as another first-choice matrix optimizer. | Schedule-Free adds state and special save/eval semantics; export the prescribed averaged iterate, not just the live weights. Prodigy’s estimated step interacts with OneCycle. First establish the optimizer screen; later compare AdamW+OneCycle with AdamW+Schedule-Free or Prodigy under one explicitly matched optimizer family. |
| **Sophia** — [Sophia](https://arxiv.org/abs/2305.14342), [implementation](https://github.com/menonpg/sophia) | Uses an intermittent diagonal Hessian estimate with clipped updates. Could be a useful curvature-informed direction for heteroscedastic regression, but it is neither Muon nor a scheduler. | Additional Hessian-estimate backward work and clipping/interval choices can change runtime materially. Its LLM result does not transfer automatically. Defer until a measured run can charge estimator overhead and provide exact optimizer-state/checkpoint tests. |

## Cheap discriminating sequence

1. **The already proposed 3-arm seed-9 cohort.** Use one exact source, data split, target/objective, schedule, seed, sampler epoch order, update budget and hardware-selected batch. Arm A is width-512 AdamW; B is width-512 Muon recurrent core + AdamW rest; C is width-768 with that same hybrid. This cleanly gives A↔B (optimizer at 512) and B↔C (width under Muon); report separate contrasts. Keep the same FP16 training scaler and require the same numerical validity/update accounting. No hidden held-out hyperparameter selection.
2. **RAdam at width 512.** Only after the first cohort’s completion and a distinct review. Compare against A at the same width/order/objective/schedule, record early scale and skip behavior. Since OneCycle already warms up, the falsifier is no reproducible improvement in fixed-fold performance or useful wall-clock after a small prespecified LR protocol; preserve uncertainty rather than treating one seed as a family verdict.
3. **NorMuon at width 512.** First add or use a bounded diagnostic for per-row norm dispersion of actual orthogonalized gate updates (no target/validation access). If dispersion is meaningful, compare the same Muon recipe with the NorMuon row-second-moment normalization only. Falsifier: no stable reduction in dispersion or no useful endpoint/cost tradeoff across independent seeds. Its 1.1B pretraining gains are not numerical priors for this task.

The later endpoint interaction is the H230 heterogeneous teacher/student path, owned elsewhere. It should test whether an optimizer-trained student improves the complete frozen blend; optimizer parents’ individual scores do not add. Keep the 99/seed-9 student/blend plan attached to that endpoint rather than multiplying this capacity screen into a seed × width × optimizer factorial.
