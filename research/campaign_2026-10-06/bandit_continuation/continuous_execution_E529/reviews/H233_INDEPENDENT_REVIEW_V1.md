# Independent H233 conditional-readout review

Reviewed 2026-10-07. This is a source/recipe review, not actor approval or experiment admission. No H233 source, recipe, split, cache, data, runtime, or ledger was changed.

## Finding

**Method implementation is coherent for a bounded, own-parent readout study, with two provenance/grading conditions for any later admission.** The frozen parent, declared C1-style target, per-control optimization, and current fold membership are consistent. The code makes no score. Fold 0 is exposed development evidence, and the valid export includes fit-development groups as well as evaluation groups; a grader must explicitly select only `evaluation_groups`. Also pin/validate the teacher-run fit provenance (or preserve a reviewed, hashed equivalent) in the frozen recipe, because the current generic binding checks the split ID and prediction bytes but does not itself prove ordinary teacher fit membership.

## Scientific and implementation checks

- **Parent ancestry and recipe fidelity:** H233 pins the own `bd26_c1v2_s3_f0` epoch-1 checkpoint, its provenance, the fold-0 manifest and the E511 anchor artifact. Runtime checks the parent args (plain two-layer GRU, 211 inputs, 23 outputs, seed 3, batch 16, chunk 2000, C1 loss/distillation/propensity settings, fixed epoch 1), exact checkpoint epoch, alias tensor equality, and feature order. It loads that checkpoint strictly, sets eval mode, disables all parent gradients and evaluates parent chunks inside `torch.no_grad()`. The readout loss matches the stated clipped-label, clipped-teacher blend (`0.3 label + 0.7 teacher`) and chunk-normalized weighted MSE on pair 0:2; it does not claim this distillation objective is the official score. The original parent auxiliary outputs and weights are retained in the checkpoint, but the candidate export is a two-output readout.
- **Fit/evaluation and teacher exposure:** H233 requires its parent fit groups to exactly match the manifest fit sets (10,535 train; 1,405 valid-fit); `CampaignSplit.assert_fit_groups` checks component exclusion from the 468 evaluation groups. I independently compared both referenced `c20261003_combo_s3_f0` and `...s4_f0` provenance memberships with the same manifest: both match the exact train/valid-fit sets and have zero evaluation-component overlap (141 evaluation components). Student training on teacher predictions for those shared fit groups is the declared own-teacher treatment; the excluded evaluation groups did not reach those teacher fits. However, the teacher sidecars are ordinary caches (no `crossfit_format`). `bind_fold_teachers` verifies run/split, manifest hash, prediction row order and prediction digest, and H233 verifies pinned teacher checkpoint/prediction digests; it does not load and assert the teacher run provenance group sets. The current checked-in provenance supports the intended exclusion, but it is not hash-bound in this recipe. Before using this as a reusable admission guard, add the provenance digest and an explicit group/component assertion, or attach an immutable reviewed provenance receipt.
- **Label separation and export:** Labels, teacher outputs and propensity weights are read in the fit path only. The export loop deliberately discards the target tensor (`for raw, _, scored in loader`) and constructs model inputs only from current raw features and the causal event context. It writes no official score. The valid export contains `valid_fit_groups ∪ evaluation_groups` by design and its `selected_mask` is merely supplied `scored` rows after warm-up; it does not remove fit-valid groups. A later grader must subset `row_groups` to the 468 evaluation groups before scoring. Scoring all rows selected by that mask would mix training and evaluation and invalidate the comparison.
- **Streaming, state and controls:** The parent recurrent state is passed chunk-to-chunk within a batch and reset at the next batch; no complete hidden-sequence cache is retained. The full input/context and target tensors for a bounded batch are still resident, while outputs are written to memmaps. Four controls have separate parameter modules, equal allocated size (22,722 each), zero-initialized final projections, separate per-control losses and gradient clipping. Their common AdamW instance maintains state per parameter, so there is no cross-control gradient/state coupling; only hyperparameters are shared. `hidden_only` intentionally leaves some allocated branches unused, as the recipe discloses. The CPU tests exercise parent freezing, zero-step identity, finite head gradients/one update, chunk/full-GRU equality and reset across batch sequences, but they do not measure production memory/throughput or test that a grader applies the eval-only group filter.
- **Profile scope:** The profile uses one actual fit-data batch and executes the requested AdamW head updates in memory, then discards them and writes no checkpoint. Read `fit_started: false` as “the full H233 fit/checkpoint run was not started,” not “no supervised optimization occurred.” The profile does not establish candidate quality. The eventual valid export is about 1.2 GB for the four prediction maps plus mask, and the recipe correctly treats its 6.5 GB fit/export limits as ceilings rather than measurements; confirm disk and device headroom at admission.
- **Claim scope:** The candidate is fold-0 development-only; no fold-generalization or public-score forecast follows. No Rust/CPU-serving, checkpoint candidate, full-data fit, export, or official metric was run in this review.
