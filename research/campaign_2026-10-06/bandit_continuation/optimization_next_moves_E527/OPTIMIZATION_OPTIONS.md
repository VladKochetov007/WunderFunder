### Reuse decoded sequence data before adding workers

The owned `SequenceFile.read` path reads one complete Parquet row group per 20,000-row sequence, selects 112 feature columns, stacks them column-major into a float32 matrix, transposes and materializes a contiguous row-major copy, then separately assembles targets and the scored mask. The features alone occupy 8.96 MB per sequence at float32, so the stack and contiguous result coexist during that conversion. `Sequences.__getitem__` repeats the row-group conversion on subsequent epochs. This is a source-derived opportunity, not proof the copies dominate: Parquet storage/page-cache behavior, target reads, feature engineering and sampler order also affect loader wait.

If the exact H230 trace shows host input wait remains material after verified cache reuse, compare the current reader against one source-hash-bound, row-major float32 feature memmap (and separately mapped labels/masks) generated with the existing reader. The cached path must preserve row-group/sample order, all feature/target bits, scored masks, split membership and reset semantics. Report conversion time, resident disk bytes, cold/warm epoch wall, loader wait, RAM/page-cache peak and end-to-end cohort wall; retain zero workers at first. The cache only wins after enough passes or fits amortize it: measured `T_build + K*T_cached < K*T_parquet` after adding any incremental upload/download and cache-verification time. Never force FP16 features into this I/O optimization—input precision belongs in a separate pair. Stop if the current loader is not critical or the cache consumes more staging/storage time than it saves.

## Optimization families

### Keep the current small GRU moving

An actual Kaggle T4 profile exists for a different raw GRU128 recipe, so a T4 is proven executable in one campaign session; that profile is not a speed result for H230's GRU256 student. If the H230-shaped recipe lacks a matched remote profile, a new full-shape profile remains the hardware gate. Record actual visible GPU count, UUIDs, compute capability, driver, CUDA/cuDNN/PyTorch versions, CPU affinity, memory and quota. Measure one explicitly visible/pinned GPU first with the frozen model, sequence, batch, chunk, cache, precision, update count, and zero workers. Add one bounded loader worker only if RAM admission has headroom.

This profile answers whether the GPU or its host can shorten a useful fit. It does not answer whether a GPU family improves the model. A future Vast offer needs the same profile before its marketing performance, VRAM, host CPU, or DLPerf value can affect selection.

For a common workload-size denominator, the H230 unidirectional GRU256×2 has an approximate forward matrix-multiply core of `3*256*211 + 3*256*256 + 3*256*256 + 3*256*256 = 751,872 MAC/row` (2 FLOP/MAC). A B16 full 20,000-row update therefore has about 240.6 billion MAC, or 0.481 TFLOP in those matrix products. ### Target recurrent compute only after a real trace

The local profile places most measured device time in recurrent forward/backward, with backward the larger phase. Keep PyTorch/cuDNN as the reference path while recording the actual kernel/operator dispatch, tensor layout, copy operations, launch count, and per-kernel time on the selected device.

The cuDNN recurrent algorithms depend on library version, input layout, dtype, shape, and GPU. PyTorch documents one persistent-algorithm condition tied to V100 and FP16; that is not a T4 or P100 promise. NVIDIA's versioned cuDNN RNN guides make Tensor Core acceleration conditional on algorithm/math mode, input/hidden/batch sizes, and tensor alignment; published rules differ by version and architecture. H230's batch 16 and hidden 256 are aligned, but its first-layer input size 211 misses both the multiple-of-8 and multiple-of-4 constraints documented by relevant cuDNN releases. Only if the actual trace shows a fallback, test a zero-padded input dimension at the smallest multiple required by the installed library (216 for an 8-wide rule, 212 for a 4-wide rule): retain the original 211 input-weight columns exactly, append zero columns to the input-gate matrix, and append literal-zero features after the existing normalization transform. The pad changes first-layer input width by 0.47% or 2.37%; under the forward matrix-only count above, it adds about 0.10% or 0.51% total GRU MAC, respectively. Those are arithmetic overheads, not measured speedups. Check full forward/state/reset, backward gradients and one matched optimizer step against the unpadded function before timing; only the real full-step comparison can show whether padding enables a faster kernel without useful-model change. P100 has no Tensor Cores, so this probe does not apply there. Inspect actual dispatch first; do not infer it from shape or from a `cudnn` label alone. A custom backward or Triton kernel only earns a fit after it beats the complete cuDNN step and passes gradient/optimizer parity.

CUDA Graphs or torch.compile are plausible if the trace finds CPU launch gaps or pointwise overhead. Start with a capture-feasibility and parity check. Include compilation and warmup, graph recapture, extra memory, AMP scaler/optimizer mutation, recurrent carry, RNG and total cohort wall time. Recurrent backward already occupies substantial measured device time, so graph capture is not a general shortcut.

### Separate physical batch, optimizer clocks, and gradient horizon

The trainer exposes three distinct controls: micro-chunk rows, macro update rows, and detach rows. Micro-chunking determines the recurrent forward pieces; update rows determine optimizer cadence; detach rows determine gradient horizon while state values can still carry forward causally. Change one of these at a time.

For a longer-gradient experiment, use one common macro update window that permits both detach schedules, then compare detach intervals while keeping batch order, examples/update, optimizer steps, clipping, schedule, EMA clock, and full official endpoint aligned. The old default of one update per chunk cannot by itself isolate a longer detach interval; both arms need a matched macro update setup.

Use activation rematerialization as a conditional bridge when the scientific question is a longer detach horizon or a wider teacher that exceeds activation memory. PyTorch's non-reentrant checkpoint path replays each selected forward segment during backward and supports `autograd.grad` and detached tensors inside a checkpointed region; RNG preservation can add overhead. The original sublinear-memory work reports this compute-for-memory tradeoff for long recurrent sequences, but it does not establish a speed or quality benefit for our GRU. First compare the same horizon with and without a checkpointed chunk function, passing the carried state through the exact wrapper and verifying forward/state/reset, gradients, AMP/scaler behavior and one optimizer update. Then, if the memory reduction is real and the extra backward wall time is tolerable, compare a longer `detach_rows` recipe against its same-horizon non-checkpointed control while holding `update_rows`, examples, optimizer clock and endpoint fixed. Capture both peak memory and full fit wall time; do not claim rematerialization itself improves quality. Preserve the same autocast context for original and recomputed forwards, and keep RNG state if stochastic ops are present. This is a compute-for-capacity component, not a change to precision or batch size.

For B16 versus B32, first test memory and throughput. A scored fit must preserve the effective examples and weighted-loss denominator per optimizer step, as well as update and EMA clocks. A physical batch that raises sequences/second can lower quality if it changes the optimization path. Report time-to-fixed-endpoint and quality, not only rows/second.

### Keep precision as a separate factor

FP16 plus GradScaler and FP32 parameters/update state is the current GPU reference. A precision ladder can compare explicit FP32 and TF32 only where supported (Ampere-class CC 8.0+), BF16 on supporting hardware, then FP8 only for compatible matrix operations. Change no batch size, target encoding, clipping, update count, optimizer, or architecture in the precision pair.

T4 supports the current FP16 route but does not provide native TF32, BF16, or FP8 Tensor Core paths. An Ada, Hopper, or newer card may expose FP8-capable operations, but Transformer Engine Linear has scaling and shape constraints and is not a replacement for the cuDNN GRU. A stronger FP8 use case may be a larger, parallel teacher whose wide linear blocks actually consume enough compute to offset quantization and layout costs. Keep recurrent state/reductions in a declared higher-precision policy and verify forward values, gradients, successful updates, checkpoint reload, and the downstream fixed student.

An 8-bit optimizer is not a GB-scale memory fix for this model: roughly 0.975M parameters imply about 15.6 MB for FP32 parameters, gradients, and two Adam moments. E525 measured optimizer work around 0.36% of CUDA event time. The existing fused optimizer is already active. A different optimizer remains a scientific quality interaction on larger teachers, but should be compared by successful full steps and endpoint value, not a standalone optimizer-kernel timer.

### Buy model capacity and useful teacher diversity

Width and architecture scale can matter more to the top-1 objective than shaving a few percent off one small fit. Keep open H070 low-rank wide recurrence, H230 heterogeneous transfer, H214 input-projection hoisting, H215 independent models per TPU chip, H216 parallel linear recurrence, H217 causal TCN, and H218 block-recurrent attention. H233–H239 remain separate untested component hypotheses. Their priors stay null.

For each new teacher candidate, record an actual full-backward resource profile before fitting. Then freeze one independently initialized teacher, one matching student recipe, source hashes, target ancestry, split membership, scoring mask and checkpoint rule. Keep teacher/source/propensity ancestry outside the evaluated student fitting groups, and keep teacher-trained labels outside any scored evaluation group used to claim transfer. If an owned model has already seen a group, use it for standalone evidence only on its declared teacher-excluded exposed unit; create a valid cross-fit/non-overlap source before measuring that teacher's student contribution. Do not add component score deltas or infer that a weaker standalone teacher lacks conditional student value.

A recurrent-rank screen can use the already open H070 lineage and existing --recurrent-rank implementation. The seeded random library fragment in [SOURCE_LEDGER.json](SOURCE_LEDGER.json) suggested inspecting singular spectra for a stable low-rank elbow. This is only a screening hypothesis: the Gaussian-ensemble result in that source is not a model-weight prior. Factorized recurrent multiplies may be slower at a small batch, so profile the actual full forward/backward path.

For TPU, E463v3's receipt lists eight visible TPU v5 lite devices, global batch 16/local batch 2 per chip, and 2,000-row chunks. One synthetic full-shape `pmap` forward/backward/AdamW update took 4.261 seconds measured across its first call (therefore including compile/dispatch, not a warmed step rate); outputs, state, gradients and updated parameters were finite, and a short export/reload check had zero max absolute error. This established hardware execution and artifact roundtrip, not training quality, warmed throughput, or Torch/JAX full-objective parity. The synthetic shards cannot expose unequal label-mass errors: first compare each loss component's global weighted numerator/denominator and gradients against an unsharded real-data oracle, then warm the full shape and compare H214 input-projection hoisting and H215 one-model-per-chip against the same recipe. Do not spend a production fit on first-call compile timing.

### Choose multi-GPU mode by useful work

Two visible GPUs can train independent seeds/teacher variants, train one model synchronously with gradient reduction, or support a distinct pipeline-parallel experiment. These optimize different quantities.

Start with two independent, UUID-pinned fits if the goal is more complete candidates per hour. Measure combined host CPU, cache duplication, RAM, pinned buffers, GPU memory, and output collection. If single-fit latency is the target, only then compare one-GPU training against DDP with fixed global examples, loss reduction, optimizer steps and schedule. The one-step delayed-gradient plus error-feedback paper concerns large pipeline-parallel LLM pretraining; it motivates a separate scientific descendant if communication bubbles are measured. It provides no prior for the current small GRU.

Do not reject DDP just because the current model is small: at about 0.975M parameters, an FP32 gradient payload is only about 3.9 MB. An ideal two-rank ring all-reduce moves about one gradient-vector's worth per rank before protocol/launch synchronization; the byte volume alone is not evidence that collectives dominate a roughly one-second measured update. Conversely, it does not promise a 2× latency reduction: each device receives only part of the global batch and the serial recurrence, host input pipeline, GPU occupancy, launch latency and shared CPU all matter. Measure a matched global-batch step and full fit; compare DDP's one endpoint latency against two independently trained, graded candidates per hour and dollar.
