## What the paper establishes

[“One-Step Gradient Delay is Not a Barrier for Large-Scale Asynchronous Pipeline Parallel LLM Pretraining”](https://arxiv.org/html/2606.30634v1) studies a specific distributed-training problem: synchronous pipeline-parallel model stages leave bubbles, while asynchronous stages can remove those idle slots by applying a gradient one update late. The paper uses PipeDream-2BW to make the delay a fixed one step, independent of pipeline depth. It contrasts that with original PipeDream’s variable stage delays.

The paper’s result is primarily about **quality under stale optimizer updates**, not a general recipe for increasing GPU utilization. On its 135M/360M SmolLM experiments, one-step delay hurts AdamW substantially more than Muon and several other optimizers. For the 360M comparison, Muon’s validation loss is 2.578 synchronous and 2.590 delayed; their update-level Error Feedback (EF) result is 2.583. At 10B MoE scale, trained for 200B tokens across a 64-GPU setup, the table reports 1.906 synchronous, 1.911 delayed, and 1.906 delayed+EF. These are large language-model results with their own tuning, batch sizes, training horizons and evaluation; they do not predict our GRU’s score or throughput.

Their EF is a parameter-update correction. With `u` denoting an optimizer update computed from the delayed gradient, the paper changes the current displacement from `-u[t-1]` to `-2u[t-1] + u[t-2]`. It stores a previous update/residual-sized state. This is **not** quantized-gradient error feedback and is not a remedy for truncated backpropagation. The paper’s appendix estimates one parameter-sized version for PipeDream-2BW and one model-sized residual for EF; those additions are relatively small per shard in its multi-GPU LLM setting, but that does not remove the software/scheduling cost of adding a pipeline to our trainer.

The Muon result is similarly conditional. In this paper Muon is an optimizer tested in synchronous and deliberately delayed LLM training. The staleness result does not show that Muon accelerates every synchronous small model. Our own `src/wnn/optim.py` implements a GRU-specific `MuonAdamW` hybrid: orthogonalized per-gate recurrent matrices with AdamW for the remaining parameters. Its CUDA orthogonalization converts gradients to BF16 and runs five Newton–Schulz iterations. That implementation is a candidate optimizer arm, not a replication of the paper’s training system. On a GPU without native BF16 Tensor Core support, this BF16 matrix path needs an actual compatibility/performance check before it is admitted.

The paper’s runtime argument is pipeline-bubble removal. Its appendix models a 16-stage pipeline and explicitly assumes communication is fully overlapped; it cautions that measured end-to-end speed depends on implementation and hardware. With one GPU (`P=1`) our current fit has no pipeline bubble to remove. Two GPUs do not automatically create useful pipeline parallelism: the model must be partitioned, activation/gradient transfers and state management added, and enough independent micro-batches supplied to hide stage latency. A two-T4 result must be measured on the actual Kaggle allocation rather than inferred from the paper’s 16-stage runs. The second GPU could also run a separate independently seeded fit, which improves cohort throughput rather than the latency of one fit and has its own CPU, storage, and admission costs.

[Egor Petrov’s personal site](https://moderntalker.github.io/) describes his research focus as efficient large-scale LLM training, parallelism, optimization and scaling laws; the [publications page](https://moderntalker.github.io/publications/) lists this paper and links to its arXiv record. The site helps identify the author and related work, but it contains no independent GPU benchmark, detailed method, or hardware availability evidence. Technical conclusions below are grounded in the arXiv paper and NVIDIA/PyTorch documentation, not inferred from the profile page.

## Keep three different mechanisms separate

| Mechanism | What changes | Relationship to our trainer |
|---|---|---|
| **TBPTT** | The forward recurrent state is carried into the next chunk, but the autograd graph is detached at a boundary. This truncates gradient credit assignment while retaining the numerical hidden-state history. | `scripts/train_rnn.py` defaults `detach_rows` to `chunk`; the ordinary path runs `forward_chunk(...)` then `detach_state(h)` at each chunk. H230 uses 2,000-row chunks. This is the current recipe’s gradient horizon. |
| **Async host-to-device prefetch** | A pinned CPU batch is copied on a CUDA side stream while the current batch runs. The copy is synchronized before consumption; model parameters are not updated asynchronously. | `--fast` enables pinned memory and `CudaPrefetcher`. This can hide input-transfer latency; it is not pipeline-parallel stale-gradient training. H230’s measured H2D event was only 0.01 ms. |
| **Asynchronous pipeline parallelism** | Different model stages work on different micro-batches, then an update may be applied using a gradient computed from an older parameter version. PipeDream-2BW deliberately makes this a one-step delay. | The current `train_rnn.py` path is a single-device `nn.GRU` trainer with no DDP or pipeline-stage implementation. TBPTT does not create a one-step stale optimizer update, and optimizer-update EF does not restore gradients cut by TBPTT. |

This distinction matters experimentally. A throughput change from pinned prefetch or more loader workers should be diagnosed as input/transfer overlap. A Muon comparison is a synchronous optimizer experiment unless we explicitly add delayed updates. An async-pipeline experiment needs a same-model synchronous control and an explicit stage/micro-batch schedule; it cannot be evaluated by merely changing `--chunk` or the detach interval.

## What our measurements say about the current GRU path

The pinned H230 profile is a full-shape profile of a 0.98M-parameter GRU256×2 with 31 outputs, batch 16, sequence length 20,000, chunk length 2,000, FP16 autocast, and zero data-loader workers. It completed 3 warmup plus 20 measured batches. The local preflight identified the physical device as a GeForce RTX 3060 Laptop GPU; this is not a T4 result and should not be treated as a Kaggle or Vast timing.

The profile reports p50 step wall 1,095.08 ms, p50 CUDA event total 675.8 ms, p50 forward 245.16 ms, backward 404.99 ms, and p50 loader wait 418.46 ms. H2D was 0.01 ms. The CUDA-event total is about 62% of step wall, but this is **not** an SM-utilization percentage: CUDA event components and loader wait can overlap, and no sampled `nvidia-smi` utilization trace or p90 was recorded. It does show that paying for a much higher peak-TFLOP GPU is not the first measured lever: input/loader/host gaps deserve attention before spending time on two-GPU gradient plumbing.

The profile peaked at 2.226 GB observed VRAM under a 5 GB observed ceiling. Its worker cgroup peak reached 6,499,999,744 bytes against a 6.5 GB cap, with an increase in `memory.events:max` but zero OOM or OOM-kill events. The pre-profile parent snapshot was mostly inactive file cache (about 4.99 GB inactive-file and 18 MB anonymous), consistent with file-cache reclamation, but the terminal attempt did not retain worker `memory.stat` at peak. Do not mislabel this as 6.5 GB of anonymous working set or claim worker RAM headroom. A fresh fit admission should capture anon/file/inactive-file and current events. The profile’s parent peak was 9.93 GB against an 18 GB parent high limit.

H230’s verified target cache occupies 13,372,801,024 bytes on disk across eight arrays. That footprint is a host-storage/page-cache concern, distinct from GPU VRAM. The trainer memory-maps cached targets and uses zero workers for this profile. The current data path therefore exposes a plausible CPU/file-cache bottleneck even though the model itself is small. Preserve worker-zero as the measured baseline; compare worker/prefetch changes only under a fresh host-memory admission and with sequence order/membership checks intact.

The trainer keeps model parameters in their default FP32 dtype (`model.to(device)` does not set a lower dtype), then applies autocast inside chunk forwards. H230’s recipe explicitly selects FP16 and `--fast`; GradScaler is enabled for FP16, while BF16 autocast uses no GradScaler. The fused AdamW path and on-device step counter reduce optimizer launch/synchronization overhead, but they do not convert the Adam moments to 16-bit. The measured optimizer segment was only 2.43 ms in the H230 profile, so an optimizer change is primarily a scientific convergence/quality question here, not the obvious wall-clock bottleneck.

## Precision and persistent-state tradeoffs

FP8 is not “INT8 with a different name.” FP8 stores a sign, exponent and fraction; NVIDIA documents E4M3 and E5M2 variants with different range/precision tradeoffs. INT8 is an integer quantization representation with scale/zero-point or related quantization metadata; integer matrix products commonly accumulate into a wider integer type. FP16/BF16/FP8 are floating-point formats. They have different conversion, accumulation, scaling, and calibration behavior.

| Mode | Numeric properties and hardware | What it means for this code |
|---|---|---|
| FP32 | 32-bit float, broad dynamic range and higher significand precision than 16/8-bit modes. | Baseline for a controlled accuracy/throughput comparison. More activation and temporary storage, but the present model’s durable Adam state is small. |
| FP16 | 16-bit float with less exponent range than BF16. T4 and newer NVIDIA Tensor Core generations accelerate FP16; P100 also advertises native FP16 arithmetic without Tensor Cores. | Current H230/E521 mode. FP32 parameters and Adam state remain; selected operations/activations use autocast. GradScaler is enabled to reduce gradient-underflow risk. Measure loss/gradient skip rate and complete-fit time. |
| BF16 | 16-bit float with FP32-like exponent range and fewer fraction bits than FP16. CUDA’s guide lists native BF16 floating-point operations from compute capability 8.0. | Current trainer accepts `--precision bf16` and disables GradScaler for it. A T4 (CC7.5) or P100 (CC6.0) is not a native BF16 Tensor Core target; RTX 3090/A40 (CC8.6), A100 (CC8.0), L4/RTX 4090 (CC8.9), and H100 (CC9.0) have native BF16 Tensor Core support. Still profile the GRU/cuDNN path. |
| FP8 | 8-bit floating point; E4M3 has more significand precision and less range, E5M2 more range and less precision. FP8 Tensor Core support starts at CC8.9 (Ada) and is present on Hopper. | `train_rnn.py` exposes FP16/BF16/FP32 autocast only; it has no FP8 recipe, scaling/amax history, or FP8 recurrent-kernel implementation. L4/RTX 4090/H100 capability alone does not make FP8 training available or beneficial for this GRU. |
| INT8 | 8-bit integer; fast Tensor Core inference/training primitives exist on T4 and newer parts, but scaling and quantization error are explicit. | Project QAT is weight-only nearest-even INT8 with an identity STE and **requires FP32 training**; it stores latent float parameters and quantizes each effective forward/export. It is not ordinary INT8 training and does not halve Adam state. Treat quantized inference as a separate deliverable with CPU/native numerical and reset parity. |

For this measured 0.98M-parameter model, a rough FP32 parameter size is 3.9 MB. FP32 parameters + FP32 gradients + AdamW’s two FP32 moments are about 16 bytes/parameter, or 15.7 MB, before small step/scaler metadata. Current autocast FP16 does not remove that persistent state; its potential savings are in forward/backward intermediates and suitable kernels. A pure 16-bit or 8-bit *serialized weight* would shrink weight storage, but that is not the same as optimizer-state storage or training compute. Quantization scales and padding add some storage, while FP8/INT8 accumulation and master-state choices depend on the implementation.

Muon’s GRU matrices keep a momentum buffer; the present `MuonAdamW` uses AdamW for other groups. This can save one Adam moment on Muon-assigned matrices, but its Newton–Schulz iterations allocate/update scratch tensors and add matrix work. For a small GRU, the few MB of state difference is immaterial to the measured VRAM peak; test end-to-end step time and training outcome instead of selecting it on parameter-memory arithmetic. The exact hardware matters: this code’s BF16 orthogonalization path should get a no-fit device/kernel compatibility check on T4 before a Muon fit is admitted.

## Conditional GPU comparison for Kaggle-native versus a later Vast candidate

These are **capability classes**, not claims that Kaggle or Vast currently offers a particular card, host, price, quota, or driver. NVIDIA’s compute-capability mapping identifies the model generations below; precision support follows NVIDIA’s compute-capability/Tensor Core tables and per-product pages. Query the actual visible name, UUID, compute capability, memory, driver, and count for each session; a model name alone does not establish a usable kernel, partition size, or throughput.

|---|---|---|

Do not pay for FP8 capability the current path cannot use. |

The **current measured device** for the H230 profile was a local RTX 3060 Laptop GPU, not a T4. The CUDA CC map lists RTX 3060 at 8.6; still record runtime capability and visible UUID in the next session rather than treating the prior local snapshot as a Kaggle/Vast guarantee.

Use this device-selection order:

1. In Kaggle, record `nvidia-smi --query-gpu=name,uuid,compute_cap,memory.total,memory.used`, the actual GPU count, driver/CUDA/cuDNN versions, and whether the GPU is shared or partitioned. NVIDIA documents this command as a supported way to query the device capability.
2. Profile the frozen full-shape batch/chunk on one visible GPU at the recipe’s precision and zero workers. Record CUDA component medians, loader wait, hardware utilization samples, VRAM, cgroup anon/file/inactive-file, and complete startup time. Do not infer utilization from TFLOPS or CUDA-event/step-wall ratio.
3. If CPU/loader wait remains large and H2D is already hidden, prioritize host preprocessing, cache access, and bounded loader experiments before selecting a much faster GPU. If CUDA compute dominates and the GPU stays busy, compare FP16/BF16-capable candidates by measured completed updates per second and memory margin.
4. If two GPUs are visible, compare (a) one fit per card for independent-seed cohort throughput, and only then (b) a synchronized data-parallel or pipeline prototype for single-fit latency. Pin each process to a unique GPU UUID and account for host CPU, RAM and cache duplication. Async PP+EF is a separate scientific/engineering experiment with a synchronous matched control.
5. When the Vast candidate token/identity is supplied, inspect its real GPU model/count/driver and available quote read-only. Do not rent or reserve a machine from this note. Compare actual matched-shape throughput, full fit time, memory headroom and any later authorized price; this note makes no availability or price promise.

## Bounded follow-up options

These are candidate experiments for separate root admission, not actions taken here.

- **Device/input profile:** repeat one frozen 3-warmup/20-timed full-shape profile on each actually available candidate GPU, with the same model/checkpoint, batch 8 then 16, chunk 2,000, precision supported by the card, and the same pinned inputs. Add time-sampled `nvidia-smi` utilization and worker/parent memory.stat collection. This determines whether T4/L4/A100/H100 differences survive the current host-data ceiling.
- **Precision pair:** on CC≥8.0 hardware, compare current FP16+GradScaler with BF16 autocast; retain FP32 as a reference. Fix the checkpoint initializer, seeds, target/cache, batch, chunk, update count, scheduler and split. Compare overflow/skip counters, loss/gradient stability, fixed checkpoint export and the same official scorer. Do not attribute a quality delta to precision if batch or schedule changes.
- **Synchronous Muon arm:** compare current fused AdamW against this repository’s GRU-gate MuonAdamW under the same synchronous recipe on a GPU where the BF16 Newton–Schulz path is supported. Measure optimizer time plus full step time, not only the orthogonalization kernel; keep the initializer/target/seed and official evaluator frozen. This tests the optimizer for our task, not the paper’s async claim.
- **Two-GPU option:** if the actual Kaggle allocation exposes two T4s, first profile concurrent independent fits with unique output paths and GPU UUID affinity under host limits. A model-parallel prototype should come later and compare synchronous pipeline versus one-step delayed PipeDream-2BW, with and without the paper’s update-level EF, identical effective batch and full metric. Preserve TBPTT boundaries in every arm and report the gradient truncation separately from optimizer staleness.

No universal result is inferred from these papers. They motivate concrete optimizer and pipeline descendants if measured hardware shows a use case; current evidence points first to single-GPU input/host timing, with FP16 as the already exercised mode.
