# Checkpoints, predictions and training diagnostics

Keep both model checkpoints and fixed-evaluation predictions. They serve different analyses. Checkpoints support new evaluation panels, different precision/serving implementations, hidden-state extraction and continued training. Saved predictions make pairwise residual analysis, static blending and component-cross-fitted stacking cheap enough to examine many models.

For each fit retain the exact selected checkpoint, normalization/preprocessing state, model configuration, source revision/hashes, source-qualified train/evaluation membership, target treatment, teacher/initializer ancestry and checkpoint hash. Keep epoch checkpoints when they support the declared scheduler/late-optimizer experiment; keep one rolling resume checkpoint with optimizer, scheduler, AMP scaler, RNG, sampler/epoch/update position and interrupted-state semantics. A weights-only checkpoint is insufficient for faithful training resumption. [PyTorch checkpoint guidance](https://docs.pytorch.org/tutorials/beginner/saving_loading_models.html).

Use existing float32 NPY plus a hash-bound metadata sidecar as the canonical dense prediction format. It is directly memory-mappable for repeated array operations. Store the row order, source hashes, sequence/component IDs, time-step order, evaluated mask, checkpoint identity, split, target names and prediction generation configuration. Use explicit file hashes; filenames alone do not prove compatibility. [NumPy open_memmap](https://numpy.org/doc/2.1/reference/generated/numpy.lib.format.open_memmap.html).

For exploratory analysis, export only the fixed scored rows to compressed Parquet, partitioned by run/fold/epoch. Columns: source ID, sequence ID, component ID, row-in-sequence, pred_t0 and pred_t1; file metadata binds the source hashes, mask and checkpoint. Labels and mask belong in one shared panel rather than repeated in every model file. Keep float32 values unchanged and use lossless ZSTD compression. Parquet supports selective column reads and row groups; actual size/read speed must be measured on our output rather than assumed. Dense NPY remains useful for distillation and serving parity. [Arrow Parquet documentation](https://arrow.apache.org/docs/python/parquet.html).

Disk allocation matters: 468 complete evaluation sequences ×20000rows ×2targets ×4bytes is74,880,000bytes before the small NPY header. All1873validation sequences cost299,680,000bytes. The current scored468-group panel contains808,863rows, so its two float32 predictions occupy6,470,904raw bytes before IDs, metadata and compression. Generating full training predictions for10607sequences costs1,697,120,000bytes per model. Retain full training targets only for admitted teacher cohorts or reusable confirmed candidates; keep other weights and regenerate those targets when needed. Never delete historical evidence automatically. Check disk before collection. The general10GB preparation reserve has a narrowly recorded exception for two checkpoint-only fold1fits: at most500MB per fit and at least2GB free before each start, under ROOT_CHECKPOINT_FIT_ALLOCATION_R2.json. This exception does not admit large prediction/cache exports.

Record during training: epoch/update, completed/skipped update, objective components, learning rate and beta1 for every parameter group, unscaled pre-clip global gradient norm, clipping threshold/event, AMP scale/overflow, wall time and sampled device/RAM usage. Log module-level norms and weight/update ratios periodically when the experiment asks about them. Historical gradient norms cannot be recovered exactly from final weights. Avoid per-step host synchronization solely for logging: buffer device scalars and flush at existing reporting boundaries; use identical diagnostics for the TPU/GPU timing comparison.

For learning-rate policy experiments, preserve the actual LR/beta traces rather than only scheduler names. Candidate policies include the existing OneCycle control, warmup+cosine, warm-stable-decay, and a separately declared plateau/noise-responsive policy. Scheduler comparisons keep the data order, initial weights, update budget and other parameters matched. Retain loss curves, gradient norms, selected checkpoint rule and full held-out predictions so a late improvement or unstable step can be diagnosed.

Prediction correlation is a screening tool, not a quality criterion. Compare residual dependence by target and component, fixed-blend contribution, meta-cross-fitted contribution and runtime. An individually weaker teacher can still be useful. Distillation, stacking and boosting require their own ancestry/membership checks; repartitioning previously exposed data does not create a fresh holdout.
