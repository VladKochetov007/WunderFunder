# Independent review: clean T3 F0 treatment Kaggle packet R4/R5

## Verdict

The R4 mount-discovery correction and R5 quota arithmetic pass static review and the declared offline fixtures. R5 is a **prepared-only** packet. It can support a root-authorized profile-only attempt with `fit_authorized=false`; it does not yet support an unconditional full-fit dispatch. Before any full-fit admission, correct the global-deadline finalization race below or establish that the admitted full pipeline terminates before that path. Root retains all release and dispatch authority.

This review did not access Kaggle, upload or dispatch a kernel, import the trainer/Torch, run inference, fit a model, or read raw Parquet payloads. The profile fixture is parser/guard compatibility evidence from an earlier T4 run, not a new R22 device qualification.

## Budget and remaining blocker

R4’s 14,400-second wall cap reserves 28,800 GPU-seconds for two T4s, exceeding the root-reported 21,712 campaign headroom. R5 corrects this to 10,000 seconds × two provisioned T4s = 20,000 GPU-seconds, leaving 1,712 against that reported snapshot. Its 300-second finalization reserve is preserved. R5 README correctly warns that the three-fit/export sequence may not finish; declared stage timeout maxima sum to 19,500 seconds (profile 1,800 + three fits at 5,200 + export 1,800 + 300 finalization), so full p3/CP5 delivery is not guaranteed by the 10,000-second cap.

There is a concrete global-deadline cleanup race in the unchanged R4/R5 wrapper. `kernel.run_one()` passes `subprocess.run(..., timeout=remaining-300)` for the runner. The frozen `scripts/kaggle_gpu_runner.py` independently resolves the worker timeout to `floor(deadline - launch - 300)` and needs the same 300 seconds to stop the worker group and write `failure.json` and `summary.json` in its exception/finally path. When a worker is limited by the remaining kernel wall time, those deadlines coincide (the outer timeout can occur slightly earlier after flooring). Python then kills the runner PID before its watchdog/finally is guaranteed to execute; the model worker was launched in its own session, so killing only the runner PID does not guarantee that worker is stopped. This undermines the README’s terminal-diagnostics guarantee on the global cap path. Earlier stage-specific timeouts below the global deadline retain cleanup time.

Even when the runner produces its failure records, the kernel does not catch `run_one()` exceptions to mark `pipeline.json` terminal; it can remain `running` or `fits_running`. A terminal collector must reconcile `summary.json`, `failure.json`, worker logs and copied artifacts rather than treat that pipeline field as completion. Recommend giving the runner time through the 300-second reserve (while keeping the internal worker deadline at `deadline-300`) and ensuring worker-group cleanup is captured before relying on the 10,000-second cap for a full-fit attempt.
