# TL3 checkpoint metadata extraction findings

The metadata-only extraction is accepted. `TL3_CHECKPOINT_METADATA_R1.json` is 52,862 bytes with SHA-256 `1dea114d0588c6d6f64df59d2db9391657ba0940c632582b476c6f2de9298f4c`; its digest and size match the captured execution record. Its eight entries match the root-admitted input manifest by exact path, byte count and SHA-256, and each checkpoint's before/after digest is identical. The admission, launch, execution and post-capture stop records agree. The unit exited successfully under 0.5 CPU, a 1.5 GB memory cap, zero swap and a 120-second runtime limit; extraction took 5.80 seconds, Torch reported CUDA uninitialized, and no training, inference, arrays or tensor values were produced.

The newly recovered checkpoint arguments materially sharpen the source-closure picture. All seven predictor checkpoint argument records store `full_valid=true`, `include_heldout_valid=true`, `valid_fold=-1` and `valid_train_fraction=1.0`, with 10,607 train sequences and 600 validation sequences. The `fin256ft_s3` and `fin256ft_s4` records say `train_source=valid`; `fbc1k_s5`, `orgbase` and `w18final_distilled_s5` say `train_source=train+valid`. These saved configurations indicate held-out validation inclusion. They are not proof of the historical loader's realized row membership, but they do not support treating this lineage as a clean-F0 control.

The records separate initializer and distillation references. `fbc1k_s5@ep3` stores an empty `init`, but names `fin256_s3,fin256_s4` as distillation sources and uses `prop_f0`. `w18final_distilled_s5@ep1` stores `fbc1k_s5@ep3` as its initializer, names `w18final_teacher` plus `w18final_fbc1k_s5,w18final_family_full,w18final_family_raw,orgbase` as distillation sources, and also uses `prop_f0`. These alias strings still need exact endpoint paths and provenance. The `fin256ft_s3/s4` model and ep1 files store matching arguments, including initializers `fin256_s3@ep3` and `fin256_s4@ep3`; the ep1 files report epoch 1, while the `model.pt` files have no epoch field. Matching schemas do not tell whether the files have equal weights or which was the terminal endpoint.

The `prop_f0` model's exact SHA-256, `9e92f26d1704f84f9170d746b372c2ba67f7fb611831865a1fc689d6b813b21c`, matches the earlier cache-sidecar claim. Its checkpoint exposes only `hidden=64` and `n_in=211`; this confirms file identity, not fit scope or preprocessing ancestry. The other predictor schemas report 211 input features. No tensor values were inspected.

The remaining closure work is to bind exact files, source/config and fit membership for the `fin256_s3@ep3`/`fin256_s4@ep3` initializers; the two `fin256_s3/fin256_s4` distillation targets; `w18final_teacher` and the three family-teacher aliases; and `prop_f0`. For each direct and transitive learned ancestor, recover realized ordered fit groups and compare them with the canonical 468 F0 evaluation groups. Also recover cache producer receipts that bind exact checkpoint endpoint, row order, preprocessing, split membership and producer source to the prediction and teacher arrays. Until those edges close, this result supports neither a clean-F0 certification nor a causal claim about the public score.
