# 2026-10-12 native Q8 operational packages

This directory contains three fixed, deterministic Q8VNNI packages in the portfolio controller’s delivery order: **B first, A second, C as the optional higher-cost mixture**. That order is not a quality ranking. The all-data endpoints have no fresh held-out estimate here, and this package makes no public-score forecast.

The filenames are `h390_s3_z4equal_q8_20261012.zip`, `h390_s3_s4_equal_q8_20261012.zip`, and `h390_s3_s4_q8_z4half_20261012.zip`, respectively. Each ZIP is below the 20 MB cap, contains a root-level `solution.py`, and has CRC-checked contents bound by its create-only build receipt.

The H390 checkpoints are `vt_all_h390_ds_homogeneous_s3_r3@ep5` (checkpoint SHA256 `04675f8220ba949c1dfb6c5796a3f25a9b8f655bb48f83c188bf8f9bacd361e0`) and `vt_all_h390_ds_homogeneous_s4_r3@ep5` (SHA256 `cefee5b51cae7b72247a26558444f526e915a9fb7ad3927abd6cc02e63018419`). Their provenance records distinct seeds and initial checkpoints, `since_weight=32`, `since_floor=0.25`, fit membership of 10,606 train plus 1,873 validation sequences, and empty evaluation-row-group sets. Both are all-data students, so validation membership is training exposure; these artifacts do not support a held-out-quality claim. Their H390/Muon-parent lineage differs from the strong fold-1 reference lineage.

The Z4 component preserves the exact previously exported merged endpoint `bd26_h230_faithful_student_seed99_muonparent_v1_core_identity_v2@ep1|z4_seed99_student_hft_alldata_v2@ep0`. Its NPZ bytes are unchanged: SHA256 `8d1c4a32f58f322427093b564a4b657475e43eb393bc384336abba4fcfad043e` in B’s `weights_1.npz` and C’s `weights_2.npz`. It is the merged trained-readout endpoint, not a bare Z4 trunk.

All three packages reuse the previously validated tiered native runtime (`v2`, `avx2`, `v3`) and its precision-aware scorer. Their `solution.py` reads the packaged `precision.txt`; direct loading from each exact ZIP reported `q8vnni` and selected the local `v3` library under CPython 3.11.16. Static ELF checks passed for every bundled library. A separate single-library scratch build was not substituted: this packet preserves the known tiered dispatch and does not claim that the unbundled alternative has equivalent fallback coverage.

Runtime checks used the exact extracted ZIPs, one CPU, and ten complete 20,000-row sequences copied without value changes from row groups 0–9 of the supplied validation parquet. The callback was exercised on every row: it returned `None` during warm-up, returned two finite values on each required row, and produced bitwise-identical prediction hashes after reset/replay. There were 400,000 callback calls per two-pass profile. Cgroup memory peaks were 213–238 MB for the three candidates under a 1 GB cap; the paired check peaked at 226 MB under a 650 MB cap, with no memory-high/max/OOM event.

Local timing is capacity evidence, not a target-hardware promise. On the Intel i9-11900H, an unpaired panel measured A/B/C at 44.969/49.825/83.332 µs per row and the existing public Q8 reference `4_z1c_z4_pair_q8vnni.zip` at 102.371 µs per row. Those first measurements overlapped other CPU work and are noisy. An independent reviewer measured B at 56.83 µs and C at 93/167 µs in its separate profile, also with concurrent CPU0 work. A later sequential paired `reference → C → reference → C` probe on CPU 2 measured 74.811, 98.927, 67.706, and 106.021 µs per row, respectively; C averaged 1.44× the paired reference time. The reference’s two paired passes also differed by about 10%, so these values do not justify extrapolating a precise full-fold runtime or a Kaggle EPYC result. No full-fold scoring, model fitting, or provider operation was performed for these packages.

`receipts/` binds package bytes, source checkpoints, provenance and exported tensors. `profiles/` contains the exact-ZIP callback profiles, static ABI checks, profile-input identity, and the short paired timing probe. The paired probe JSON explicitly records its CPU affinity, cgroup bounds and alternating order. The historical reference package has no create-only build receipt, so its profile uses a clearly labeled adapter binding the exact ZIP and every member hash; the adapter is not a build or provenance receipt. The independent package review is commit `88faf7eabb55f19385d3ddc1796d76dd53b259c3`; it confirmed source/member binding and bitwise parity on B/C.
